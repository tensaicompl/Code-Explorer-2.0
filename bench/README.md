# bench

The benchmark harness's data: pinned repositories, committed corpus, expected graphs, reviewed samples and results.

Contents arrive with the task that produces them.

## repos.lock

The benchmark repositories, pinned by commit: `[[golden]]` entries (one per language
benchmarked, indexed by the golden harness, with a permissive licence) and `[[scale]]`
entries (nightly timing only, never redistributed). The harness uses the pinned
`commit` and nothing else: never a branch head, tag or newer commit, and it never
repins. Changing a pin is a recorded decision, not a harness run.

## .cache/

The harness's disposable working area, git-ignored: pinned checkouts
(`repos/<lang>/<repo>/`, and `repos/scale/<name>/` for scale repositories), the
segments `pdx index` writes (`segments/`), goldens staged before they are compared or
accepted (`generated/`), the benchmark builds' caches, segments and staged results
(`bench/`), the engine differential's canonical rows and differences
(`engine-differential/`), an empty hooks directory and an empty Git configuration. Delete any of it
at will; the next run rebuilds it. Once every pin is here, `make golden`,
`make determinism` and `make perf` need no network.

## engine-differential.toml

The engine differential's corpora (P2-16, decision 50): what `make engine-differential`
runs the vendored engine and the pinned, unmodified reference engine over, nightly, and
compares row for row: definitions, call sites and callable references, imports, each
file's cross-file surface and every typed answer. Every corpus is an explicit, sorted
list of files, so a change in what is compared is a reviewed change to this file:

- `[[fixture]]`: every typed-resolution fixture of `engine/tests/fixtures/resolve`,
  every file of it listed as compared or as support (metadata staged for the engines,
  never compared). Every typed-tier language of the matrix has at least one.
- `[[golden]]`: 2 to 10 related files of every typed-tier golden repository at the
  commit `repos.lock` pins, with a sentence on what they exercise. Only the paths are
  committed; the source is read from the golden checkout under `.cache/repos/`. A
  subset is staged without repository metadata, so its relations are chosen to need
  none, and each C or C++ file is at most 32 KiB.

The staged files are the engines' only inputs, given by absolute path: both run from a
fresh empty working directory of the harness's own, never the corpus root (decision 52).
`pdx-bench differential-corpora` checks it against the language matrix and the lock
(a test does so on every `make check`) and fetches the goldens as `make golden` does.
A difference is a finding, never a new baseline: there is nothing to accept. The full
canonical rows and any difference of the last run are under
`.cache/engine-differential/<corpus>/`.

## golden/

`golden/<lang>/<repo>.expected.json`, one per `[[golden]]` entry. Each holds the
repository's structural graph as plan 5.7 describes it and decision 44 formats it: the
count of every node kind, and every drawn edge as `(src_qn, dst_qn, kind, band)`,
sorted. Goldens are generated by `pdx-bench golden --accept`, reviewed, and committed
with a justification. They are never edited by hand. They hold qualified names, kinds
and bands only: never source, paths, ids or anything about the machine that built
them. `make golden` checks them against a fresh index of every pin (see
`crates/pdx-bench/README.md`).

## results/

`results/<version>/` holds the determinism and performance baselines (P2-14,
decision 49), one `<repo>.json` per repository and `summary.json`, written by
`pdx bench` (`make determinism`, `make perf`); `crates/pdx-bench/README.md` gives the
format. They are measurements of one machine, recorded with what it is, never a
threshold: G1 sets thresholds. Normal CI does not run them: they need the network the
first time, the scale repositories and minutes to hours.

How the numbers are taken:

- **Determinism.** Each golden is built three times, each in a fresh process: a cold
  extraction cache with one Stage 2 worker; an independent cold cache with as many
  workers as the machine offers; and the second cache again, warm. The three segments
  must be byte-identical (compared in chunks, with the first differing byte reported),
  and each must hash to the `content_sha256` its build reported. The cold builds must
  have read nothing from their caches and the warm one every extraction the cold one
  stored, so the third build proves rebuild equivalence (4.13.3).
- **Samples.** Three per repository, each in a fresh process with a fresh, cold cache,
  Stage 2 at the machine's available parallelism and the default 512 MiB memory
  budget, whatever the cgroup or environment says (the harness refuses `PDX_WORKERS`,
  `PDX_MEM_BUDGET_MB`, `PDX_ENGINE_ISOLATE` and the engine's extraction switches). The
  engine runs in the sampled process. A baseline is ready only.
- **Stage times.** From the pipeline's own progress events, in integer nanoseconds:
  every stage must start and finish once, in order. The whole build's wall time is
  measured separately, around the build. Medians are of the three samples.
- **Throughput.** The files given to extraction per second of Stage 2 and Stage 3
  together: `files / (extract_ns + resolve_ns)`. The median of the three is reported.
- **Peak resident memory.** Sampled from the harness, outside the measured process, by
  the operating system's account of its resident set: once as it starts, then every
  10 ms, the last sample just before its exit is seen. The peak is the largest sample;
  the baseline is the largest of the three samples' peaks, never a median. Growth
  between the last sample and the exit is not seen, so the peak is a lower bound short
  by at most one interval's growth. If no sample can be read, the measurement fails.
- **The memory ceiling.** A worker whose resident memory exceeds 6 GiB is stopped at
  once, so a repository too large for the machine ends as a recorded outcome rather
  than taking the machine down. A golden over it fails the run. A scale repository over
  it is recorded as `out_of_memory`, with the peak seen, the stage reached, the stages
  finished and the extractions cached by then, and the summary says it did not
  complete (issue 82).
- **Nothing tuned.** The harness does not change the processor governor, set affinity,
  disable turbo or stop other work: the numbers are those of the machine as it ran,
  recorded beside its operating system, architecture, processors, memory and processor
  name, never its host name, user or paths.
- **Engine residuals.** Issues 77 to 80 (C-family callables only the expanded text
  represents, Kotlin's delegate spans, the walk's frame leak in error-recovered regions,
  C++ parse artefacts) are open and unchanged: the baselines measure the engine as it
  is, residuals included.

`results/legacy-compare.md` is P2-13's triage of how the legacy graph's drawn calls
differ from PDX's drawn `CALLS` on the Python golden: counts of same, only-legacy and
only-new source/target pairs, and 20 sampled differences explained by reading the
source. It is no accuracy oracle: the legacy graph is evidence of where the two differ,
not of which is right. `scripts/compare-legacy.py` produces the counts and the
evidence, under the ignored `.cache/legacy-compare/` with the rest of the raw run; the
explanations are written by hand, never by the script.

`results/a0/` is A0.1 and A0.2's structural-accuracy audit (decision 64, issue 95,
gate G1b): the Python and Rust goldens, and PDX itself as a diagnostic corpus,
measured with 4.13.1's precision, recall and oracle-verifiable fraction against
`scip-python` and `rust-analyzer`'s SCIP indexes, with counterfactual re-scoring.
`results/a0/methodology.md` gives the oracles, the matching rules and how
`scripts/a0/run.py` reproduces it. It is not P5-06.

## a0/

`a0/sanity/` holds A0.1's oracle sanity fixtures, one small Python package and one
Rust crate. Each call case is marked `A0: <case> -> <expected>`, and
`scripts/a0/sanity.py` checks the oracle mapping against every mark before any
whole-repository number is accepted.

## corpus/

The sanitizer corpus: small source files that `make check-asan` extracts with the
engine built under the address, undefined-behaviour and leak sanitizers, through the
engine test `corpus_extracts`, and that `abi_no_output` resolves with nothing written
to either output stream. The nightly build runs both.

Every file is written for this project. Nothing is copied from the golden or scale
repositories, whose sources are never redistributed, or from anywhere else.

The layout is the contract, and the test enforces it:

- Each top-level directory is named after an engine language ID, and every file
  beneath it is a source in that language. A file at the top level, a directory named
  after no known language, or a hidden entry fails the run; nothing is skipped.
- Every language the engine's tests cover has at least one file: the language
  matrix's 31 (`pdx_core::languages`) and the engine's `tsx` grammar, as listed in
  `engine/tests/matrix_languages.h`, which a Rust test keeps equal to the matrix.
- The corpus holds at most 200 files. It is meant to stay in the tens: one file per
  shape worth exercising, not size for its own sake.
- A file's name declares the status extraction must give it: `recovery_*` is source a
  parser has to recover from and may come back parsed or partial; `failed_*` is source
  the engine refuses by design and must fail with a diagnostic; any other file must
  parse.

The files are meant to reach the code that tends to hide memory and undefined-behaviour
defects: nesting, generics and templates, macros and the preprocessor, annotations and
decorators, escaped, multi-line and non-ASCII strings, inheritance, and source a parser
has to recover from.
