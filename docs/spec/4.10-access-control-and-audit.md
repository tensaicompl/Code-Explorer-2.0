# Access control and audit

> **Normative.** Changing this document requires a specification change request
> recorded in `docs/plan/ISSUES.md`, and where a stored format is affected, a bump
> of the relevant version constant.
>
> Mirrors section 4.10 of the implementation plan, which is not committed.

## Roles

There are exactly three roles.

- `admin`: settings, repos, principals, tokens, annotations approval, and garbage
  collection (GC).
- `maintainer`: annotations approval, pull request overlays, and re-index requests.
- `reader`: no administrative or approval capability beyond reading.

## Repository permissions

A principal may read a repository if the `repo_permissions` table has a row for that
principal, or a row for any group of which the principal is a member.

Rows are produced by the `permsync` job, which derives permissions from the host
concepts of each supported code host:

- GitLab: project members, including members inherited from groups.
- GitHub: repository collaborators and teams.
- Bitbucket Data Center: project permissions and repository permissions.

`permsync` runs every `PERMSYNC_INTERVAL`, which is 15 minutes, and additionally runs
on webhook `member` events. Administrators may add rows with source `manual`.

## Enforcement point

Enforcement happens at query planning, before any aggregation.

The set of segments a request may touch is the intersection of `manifest_segments`
with `permitted_repos(principal)`.

### Strict metadata mode

**Strict metadata mode is the default.** Under it:

- A principal receives no identifier, no name, no count, no label, no contract key
  and no aggregate that reveals an unpermitted repository.
- Link-layer edges with one denied endpoint are omitted.
- Aggregated edges and tiles (section 4.11.4) are computed from permitted
  repositories only.

The environment key `PDX_METADATA_VISIBILITY=aggregate` relaxes strict metadata mode.
It may be set by deployments that accept the resulting leakage. In the relaxed mode,
anonymous redacted counts of the form `{redacted: true, count}` are returned in place
of the omitted items.

## Tokens

Personal access tokens (PATs) are hashed with argon2id. The token scopes are
`mcp:read`, `api:read` and `admin`.

OIDC access tokens are validated by JWKS, with `aud` equal to `PDX_OIDC_AUDIENCE`.

## Audit

Every MCP tool call, every API request and every admin action writes exactly one
`audit_log` row (Part 4.4).

The columns of that row are defined in `4.4-control-plane.md`, which is
authoritative for the schema. They are repeated here for convenience and this
list is not normative:

- `audit_id`: the row's primary key.
- `at`: the timestamp, defaulting to the time of writing.
- `principal_id`: the acting principal.
- `client`: the calling client.
- `surface`: one of `mcp`, `api`, `ui`, `admin`, `cli`.
- `action`: the tool call, request or admin action performed.
- `manifest_id`: the manifest the request was resolved against.
- `repo_ids`: the repositories touched.
- `args_hash`: the arguments hash.
- `result_rows`: the number of rows returned.
- `result_bytes`: the size of the result.
- `latency_ms`: the observed latency.
- `outcome`: the outcome of the action.

Arguments are stored as a SHA-256 hash, not verbatim.

Retention is `AUDIT_RETENTION_DAYS`, whose default is 365.

Export is by `pdx server audit export --from --to`, which emits JSONL.

## No telemetry

No telemetry leaves the deployment. The only permitted outbound calls are to:

- the configured Git hosts,
- the OIDC provider,
- the segment store,
- the optional model endpoint for the chat dock,
- and, optionally, the OTel collector for the server's own traces (Part 4.14.4).
