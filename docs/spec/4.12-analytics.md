# Analytics specification

> **Normative.** Changing this document requires a specification change request
> recorded in `docs/plan/ISSUES.md`, and where a stored format is affected, a bump
> of the relevant version constant.
>
> Mirrors section 4.12 of the implementation plan, which is not committed.

## Scope and storage

All analytics are computed by the `analytics` job per manifest version (server), or by
`pdx analyze` (local, single repo).

Results are **findings**: JSON rows with the fields

- `kind`,
- `severity`, one of `info`, `warn`, `error`,
- `scope`,
- `evidence[]`.

Findings are stored in `analytics/<manifest_version>/findings.db` and summarised into
`metrics_ts`.

## 4.12.1 Per-symbol metrics (Stage 4, in segment)

Per-symbol metrics are computed in Stage 4, inside the segment. The metrics are:

- `loc`
- `cyclomatic`
- `cognitive`
- `loop_depth`
- `transitive_loop_depth`, propagated along drawn `CALLS` edges, with cycles flagged
  `recursive`
- `fan_in`
- `fan_out`
- `importance`

The importance formula is:

    importance = sqrt(fan_in) × visibility_factor × test_penalty

with factors:

- `visibility_factor` = 1.0 for public symbols, 0.6 for non-public symbols.
- `test_penalty` = 0.3 for test nodes.

## 4.12.2 Architecture rules

Rules come from `pdx-arch.yaml` and from the repo's `pdx.toml [rules]` table.

The rule forms are exactly these four:

1. `forbid {from_role, to_role, edge}`
2. `forbid {from_context, to_context}`
3. `forbid_cycles {level}`
4. `require {from_role, to_role_any_of}`

Rules are evaluated against drawn edges only. Each violation is a finding whose evidence
is the constituent L5 edges. Severity is `error`.

## 4.12.3 Cycles

Tarjan strongly connected components (SCC) over `IMPORTS ∪ CALLS ∪ USES_TYPE`.

The algorithm runs at three levels:

- module level (per repo),
- service level (link layer),
- context level.

Each SCC with size greater than 1 is a finding listing the members and the minimum
feedback edge set.

## 4.12.4 Blast radius

Transitive drawn-edge reverse closure from the changed symbols to depth `d`, then upward
to:

- files,
- services (via containment),
- contracts (via `EXPOSES` / `CONSUMES` on any touched symbol),
- deployments.

Blast radius reports counts per band, and the number of `candidates` rows encountered on
touched files as `unresolved_touched`, which is surfaced as a warning.

## 4.12.5 Contract drift

For each `ApiContract` key, compare spec definitions (OpenAPI) against implementations
(routes) against consumers. The findings are exactly these four kinds:

- `contract.undocumented`: a route without a spec.
- `contract.unimplemented`: a spec without a route.
- `contract.orphan_consumer`: a consumer without a provider.
- `contract.version_skew`: a `DEPENDS_ON_ARTIFACT` with a version range, or a version
  mismatch across repos.

## 4.12.6 Hotspots and co-change

Input is `git log --numstat --since=<HOTSPOT_WINDOW_DAYS=180>` on the server checkout,
giving churn per file.

Hotspot score:

    hotspot score = rank_percentile(churn) × rank_percentile(max cyclomatic in file)

The top decile produces the finding `hotspot`.

Co-change:

- Consider commits touching at most `COCHANGE_MAX_FILES` (20) files.
- Pairs with at least `COCHANGE_MIN` (3) shared commits produce `CHANGES_WITH` edges
  with `coupling = shared / min(commits_a, commits_b)`.
- Cross-repo pairs are computed when both repos' logs contain the same `Change-Id` or
  issue key pattern (`[A-Z]+-\d+`) within the window.

## 4.12.7 Ownership

Per file:

- top authors by lines in the window, from a `git blame` summary sampled by
  `git log --numstat`,
- CODEOWNERS entries,
- bus factor, defined as the number of authors covering 50% of changes.

Finding: `ownership.single_author` for files with bus factor 1 and a hotspot score in the
top decile.

## 4.12.8 Duplication

MinHash with 128 hashes over 5-token shingles of identifier and keyword tokens, computed
per `Function` or `Method` of at least 15 lines.

Locality-sensitive hashing uses 16 bands of 8 rows (16×8).

Pairs with an estimated Jaccard similarity of at least 0.85 produce `SIMILAR_TO` edges.
These edges are drawn only in the Findings view, never in the architecture map.

## 4.12.9 Observed edges (OpenTelemetry)

`POST /api/v2/traces/otlp` accepts OTLP/HTTP JSON spans.

Server-to-server spans whose `peer.service` or `server.address` matches a `Service`'s
known hostnames (from `pdx-arch.yaml contexts[].repos[].hostnames`, or Kubernetes Service
names in `Resource` nodes) either:

- set `observed = 1` on the matching `HTTP_CALLS` or `RPC_CALLS` link edge, or
- insert a runtime-only link row with `band = NULL, observed = 1` when no static link
  exists.

Two findings list the differences:

- `topology.observed_not_declared`
- `topology.declared_not_observed`

## 4.12.10 Freshness and index health

Per repo:

- `lag_seconds`, being head time minus newest segment build time,
- `band_coverage`, being drawn call sites divided by total call sites,
- `degraded` flag,
- `precise_available`.

Per estate:

- p50 and p95 lag,
- repos with `failed` segments,
- rebuild-equivalence rate (4.13.3).

## 4.12.11 Agent usage

From `audit_log`:

- calls per tool per day,
- calls per principal, anonymised for non-admin views,
- empty-result rate,
- median result bytes,
- follow-up grep rate, defined as a `Grep` hook event within 30 s after an MCP call with
  empty results. Hook events are reported by the local `pdx hook` to
  `POST /api/v2/events` only when `[server] report_hook_events = true`, which defaults to
  `false`.
- feedback verdict counts per band.
