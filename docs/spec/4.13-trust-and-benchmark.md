## 4.13.1 Harness

`pdx bench` is the benchmark harness. It lives in the crate `pdx-bench` and is part of the open tier.

### Repositories under test

The harness runs against `bench/repos.lock`.

The golden repositories are public, pinned by commit, and measured on every
benchmark run. The lock file holds the commits and the verified licences and is
authoritative; the mapping below records which language each repository measures.

A golden repository may be replaced when it cannot be fetched or its licence stops
being permissive, because the committed corpus draws files from these repositories.
A replacement is recorded in the lock file next to the repository it replaced,
together with the reason, and the accuracy numbers for that language are from then
on measured against the new corpus.

### Two indexes per golden repository

For each golden repository the harness builds the **structural** segment and, separately, the compiler index. The compiler index is the oracle: the structural band is measured against it, band by band and language by language.

### Accuracy measures

For each language and each band the harness reports the following three ratios.

- **Precision.** Numerator: drawn structural edges whose site has a compiler verdict and whose target the compiler confirms. Denominator: drawn structural edges whose site has a compiler verdict.
- **Recall.** Numerator: compiler call relations at parsed call sites that a drawn structural edge reproduces. Denominator: all compiler call relations at parsed call sites.
- **Oracle-verifiable fraction.** Numerator: drawn edges with a compiler verdict. Denominator: all drawn edges.

Sites without a compiler verdict are excluded from precision and are themselves reported. The oracle-verifiable fraction is the published measure of how much of the drawn graph the oracle could adjudicate at all, so precision is never read without it.

### Ingestion fidelity

Ingestion fidelity of the precise merge is measured separately from the three accuracy ratios, and is reported as its own group of measures:

- documents mapped,
- definitions mapped,
- occurrences mapped,
- ambiguous mappings,
- relationships imported,
- round-trip target fidelity.

### Precise band accuracy: not self-measured

The `precise` band's own accuracy is **not** measured against the index that produced it. Measuring a band against its own source would be circular and is prohibited.

Instead, the `precise` band is spot-checked on a stratified sample, with a minimum of 200 sites per language.

### The one human artefact

The reviewed precise sample is the single artefact in the plan that a human must supply.

- The agent generates `bench/precise-sample/<lang>/sample.jsonl`. Each record carries the site, the provider target, the structural target and a snippet.
- A reviewer writes `truth.jsonl` next to it, at `bench/precise-sample/<lang>/truth.jsonl`.
- The agent consumes the committed truth set and **never** edits it. Having generated the sample, the agent records an issue requesting review and continues with independent work.

Until `truth.jsonl` exists for a language, the trust page shows that language's precise accuracy as `unreviewed`, and gate G4 passes on its other criteria. Gate G7 requires reviewed truth for every precise-capable language.

### Timing measures

The harness reports, per golden repository:

- files per second,
- peak resident set size,
- wall time per stage.

### Determinism and differential checks

- **Determinism.** Two builds of the same pinned commit produce identical `content_sha256`.
- **Engine differential** (P2-16, nightly). The vendored engine's extraction rows and typed-resolution rows are byte-identical, after canonical ordering, to those of the pinned unmodified reference engine on the same fixtures.

## 4.13.2 Outputs

The harness writes:

- one result file per repository at `bench/results/<pdx_version>/<repo>.json`,
- one aggregate at `bench/results/<pdx_version>/summary.json`.

`docs/trust/` is a static page generated by `scripts/trust-page.py` from those summaries. CI publishes the page on tagged releases.

## 4.13.3 Rebuild equivalence

Resolution always runs over the whole repository (section 4.5), so the only cache is extraction. Rebuild equivalence is therefore a property of the extraction cache alone.

Method: the harness builds each golden repository twice, once with a cold cache and once with a warm cache, and asserts identical `content_sha256` for the two builds.

The resulting rate (100% expected) is published, so that the cache can never silently change results.
