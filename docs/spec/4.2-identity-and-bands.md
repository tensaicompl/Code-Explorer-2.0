## 4.2.1 Node identity

- `repo_id` is a **registered identity, not a URL**: on the server it is assigned once at registration (`repos.repo_id`, 16 lowercase hex chars generated randomly) and never changes when the clone URL, name or host project moves; `repo_aliases` records every URL the repo has had. The local binary uses the server's `repo_id` whenever a server is configured (obtained from `GET /api/v2/repos/resolve?url=` at first contact and cached in `.pdx/repo.toml`); with no server it derives `repo_id = sha256(canonical_clone_url)[0..16]` and records `repo_id_source = "url"` in `meta`, and a later connection to a server re-keys the local cache (node ids are recomputed; nothing persisted outside `.pdx/` depends on the local id). `canonical_clone_url` is the HTTPS clone URL without credentials, without `.git`, lowercased host, path as-is.
- `node_id` = `base32-crockford(sha256(repo_id || 0x00 || kind || 0x00 || path || 0x00 || qualified_name || 0x00 || disambiguator))[0..26]` (26 characters, 130 bits).
  - `kind` is the node kind string from 4.2.3.
  - `path` is the repository-relative POSIX path of the defining file (`""` for repo-level nodes).
  - `qualified_name` is the language-specific fully qualified name produced by the engine (Appendix B lists the per-language rule).
  - `disambiguator` is `""` except for overloaded callables, where it is `sha256(normalised_signature)[0..8]`; `normalised_signature` is the parameter type list as declared, with whitespace removed, generic arguments erased to their raw type and language-specific default aliases expanded (Appendix B.1). Only when two overloads have identical normalised signatures (possible in dynamically typed languages) is the ordinal of the overload in file order appended (`"…-1"`, `"…-2"`). Inserting an overload therefore never renumbers existing methods. Line numbers are never part of the id.
- For `Repo` nodes `path = ""` and `qualified_name = ""`; for `Folder` and `File` nodes `qualified_name = path`.
- Cross-repo nodes (contracts, artifacts, systems, contexts) use `repo_id = "estate"`, `path = ""` and `qualified_name` = the contract's **`namespace_key`** of 4.7.1 (identity + normalised key; for `unresolved` identity the key is prefixed with `unresolved:<repo_id>:` so that unresolved contracts never collide across repos), or the `pdx-arch.yaml` id. The same contract therefore produces the same `node_id` in every segment that mentions it, and `/health` in two services produces two nodes.
- `site_id` identifies a call site (or any evidence site) independently of line numbers: `base32-crockford(sha256(file_path || 0x00 || enclosing_node_id || 0x00 || site_kind || 0x00 || ast_fingerprint))[0..26]`, where `ast_fingerprint` = sha256 of the engine's node-type path from the enclosing definition to the site plus the callee/receiver text and the ordinal of that (path, text) pair within the definition. Byte offsets and lines are stored on the site but are not part of its identity.
- `edge_id` = `base32-crockford(sha256(src_node_id || dst_node_id || edge_kind || site_id))[0..26]`. The site is part of edge identity because the same pair can be linked from many sites; identity survives line shifts.

### Byte-level encoding

The formulas above are exact under these rules, approved on 2026-10-02 (`docs/plan/ISSUES.md`, issue 33). They are the identity format of `SEGMENT_SCHEMA_VERSION` 1: once segments exist, changing any of them is a change of stored format.

1. **Strings.** Every field is hashed as its UTF-8 bytes, without terminator or normalisation. `||` is byte concatenation and `0x00` a single zero byte. No field may contain a zero byte; an implementation refuses such input rather than hash it.
2. **`sha256`** is SHA-256 over the concatenated bytes, giving a 32-byte digest.
3. **`lowerhex(d)[0..k]`** writes the digest as lower-case hexadecimal, two characters per byte, high nibble first, and keeps the first `k` characters.
4. **`base32-crockford(d)[0..26]`** reads the digest as a bit string, starting with the most significant bit of its first byte, and writes each successive group of 5 bits as the symbol at that index of the alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, in upper case. The first 26 symbols are kept: the digest's first 130 bits. There is no padding and no check symbol.
5. **`repo_id` derived from a URL** (local binary with no server only; a registered `repo_id` is never derived) is `lowerhex(sha256(canonical_clone_url))[0..16]`. `canonical_clone_url` is defined for an `https` clone URL, `https://[userinfo@]host[:port]/path`, and is formed by:
   - matching the scheme in any case and writing it `https://`;
   - removing the user information, everything up to and including the last `@` before the host;
   - lowercasing the host and keeping an explicit port exactly as written;
   - keeping the path byte for byte, except that one terminal `.git` is removed.

   Any other input has no URL-derived identity and is refused: another scheme (including `http`, `ssh` and the `user@host:path` form), no host, no path or a path of `/` alone, a query, a fragment, or a space or control character anywhere.
6. **`node_id`** hashes its five fields with one `0x00` between consecutive fields, and none before the first or after the last. `repo_id` is the 16-character id, or `estate`; `kind` is spelled exactly as in 4.2.3.
7. **The disambiguator.** Callables that share a `kind`, `path` and `qualified_name` form an overload group, listed in file order.
   - A callable alone in its group has the disambiguator `""`.
   - In a larger group, each member's disambiguator is `lowerhex(sha256(normalised_signature))[0..8]`.
   - Members whose normalised signatures are identical each have `-` and an ordinal appended: the member's position among those identical signatures in file order, in decimal, counting from 1 (`…-1`, `…-2`).

   Inserting an overload with a distinct signature therefore changes no existing id. A callable that was alone changes its id once, when it gains its first overload, because its disambiguator changes from `""` to its signature's.
8. **`ast_fingerprint`** is `lowerhex(sha256(n || 0x00 || type_1 || 0x00 || … || type_n || 0x00 || callee_text || 0x00 || receiver_text || 0x00 || ordinal))`, the full 64 characters, and is stored in that form in `sites.ast_fingerprint`.
   - `type_1 … type_n` are the engine's node types from the enclosing definition to the site, each non-empty, and `n ≥ 1` is their count in decimal ASCII without leading zeros.
   - `callee_text` is the callee for a call and, for any other site, the site's text, as the `sites` row stores it; `receiver_text` is the receiver, or `""` for none.
   - `ordinal` is the site's position, in decimal counting from 1, among the sites of the same enclosing definition with the same path, `callee_text` and `receiver_text`, in source order.
9. **`site_id`** hashes its four fields with one `0x00` between consecutive fields.
   - `file_path` is the repository-relative POSIX path.
   - `enclosing_node_id` is the 26-character id, or `""` for a site outside every definition.
   - `site_kind` is one of `call`, `reference`, `import`, `type_ref`, `field_rw`, `route`, `contract`.
   - `ast_fingerprint` is its 64-character stored form.
10. **`edge_id`** concatenates its four fields with no separator: `src_node_id` and `dst_node_id` (26 characters each), `edge_kind` spelled exactly as in 4.2.4, and `site_id` (26 characters, or `""` for an edge with no site). Fixed-length ids and a closed vocabulary of kinds make the concatenation unambiguous.

## 4.2.2 Confidence bands

Every edge of kind `CALLS`, `USES_TYPE`, `INHERITS`, `IMPLEMENTS`, `OVERRIDES`, `IMPORTS`, `HTTP_CALLS`, `RPC_CALLS`, `PUBLISHES`, `SUBSCRIBES`, `READS_TABLE`, `WRITES_TABLE`, `LINKS_ARTIFACT` carries `band`. Bands, in descending confidence:

| Band | Meaning | Source | Drawn |
|---|---|---|---|
| `precise` | Confirmed by a compiler-backed index (SCIP/libadalang) | 4.6 | yes |
| `typed` | Engine type resolution reached exactly one target | engine strategy `lsp_typed` with `candidates == 1` and score ≥ `TYPED_MIN_SCORE` (0.85); no other engine strategy can produce `typed` | yes |
| `import-guided` | Name resolution restricted by the file's imports reached exactly one target | Rust resolver | yes |
| `inheritance-guided` | Method resolved through the receiver's class hierarchy to exactly one target | Rust resolver | yes |
| `exact` | The name has exactly one definition in the repository | Rust resolver (the engine's `unique_name` result is only a hint; the Rust registry decides) | yes |
| `scoped` | Exactly one definition in the same module/package | Rust resolver | yes |
| `candidate` | More than one surviving candidate, or engine score < `TYPED_MIN_SCORE` and > 0 | engine `suffix_match`, `fuzzy_single`, `fuzzy_multi`, `service_pattern` | **no** (stored in `candidates`) |
| `external` | Target is outside the repository (stdlib, third-party) | resolver | no (counted) |
| `blocked` | Callee name is on the generic-name blocklist (Appendix B.4) | resolver | no (counted) |
| `unresolved` | No candidate | resolver | no (counted) |
| `contradicted` | A drawn edge that a precise index says does not exist | 4.6.4 | no (kept for audit) |

`observed` is not a band. Runtime observation (4.12.9) is an orthogonal flag: an edge or link may be `typed` and observed, `precise` and observed, or a runtime-only relation with `band = NULL` that exists only in the link layer. Observation never promotes or demotes a band. Bands are therefore 11.

Rules:

1. The engine's numeric score, strategy string and candidate count are stored verbatim on the edge or candidate row (`engine_score`, `engine_strategy`) for calibration; the **band** is what all consumers use.
2. Only `Drawn = yes` bands appear in the graph, tiles, MCP traversal results and blast radius. Non-drawn items are reachable through `coverage` and `candidates` tools/API only.
3. A precise index **upgrades** a drawn edge to `precise` when it confirms it at the same site, **adds** missing call edges as `precise` only where a compiler occurrence intersects a structural call site, and **demotes** a drawn edge to `contradicted` when the precise index resolves the same site to a different target. Two precise sources that disagree on one site produce `conflict` rows in `evidence` and neither target is drawn as `precise`. Observation flags are never touched by precise merging.
4. Calibration: the benchmark harness (4.13) measures precision per band per language; the published numbers are what the trust page shows. The band *ordering* above is fixed; the *thresholds* (`TYPED_MIN_SCORE`) may be tuned only by a Specification Change Request with new measurements.

## 4.2.3 Node kinds

Structural (per repo): `Repo`, `Folder`, `File`, `Module` (package/namespace/Ada package), `Class`, `Interface`, `Enum`, `Struct`, `Trait`, `TypeAlias`, `Function`, `Method`, `Constructor`, `Field`, `Variable` (module-level), `Macro`, `Route` (HTTP endpoint handler binding), `Test`, `Resource` (K8s kind instance), `ConfigKey`, `Doc` (markdown section).

Contract (estate-level, owned by producing repo): `ApiContract` (OpenAPI operation or route template), `RpcMethod` (protobuf/gRPC), `Channel` (AsyncAPI channel, Kafka topic, queue), `Table`, `Column`, `Artifact` (build coordinate `group:name`), `ArtifactVersion`.

Architecture (estate-level): `System`, `BoundedContext`, `Service`, `Library`, `Database`, `Broker`, `Frontend`, `BatchJob`, `Deployment`, `LayerRole` (values: `api`, `service`, `domain`, `persistence`, `adapter`, `port`, `infra`, `test`, `unknown`).

## 4.2.4 Edge kinds

Containment: `CONTAINS` (Repo→Folder→File→Module→Class→Method etc.; exactly one parent per node except `Repo`).
Structural: `CALLS`, `CALL_REFERENCE` (callable passed as value), `USAGE` (identifier used, target not proven), `IMPORTS`, `INHERITS`, `IMPLEMENTS`, `OVERRIDES`, `USES_TYPE`, `READS_FIELD`, `WRITES_FIELD`, `THROWS`, `TESTS`, `DEFINES_ROUTE`, `READS_CONFIG`.
Contract: `EXPOSES` (Service/Route→ApiContract|RpcMethod), `CONSUMES` (call site→ApiContract|RpcMethod), `PUBLISHES`, `SUBSCRIBES`, `READS_TABLE`, `WRITES_TABLE`, `DEFINES_TABLE`, `PRODUCES_ARTIFACT`, `LINKS_ARTIFACT`.
Derived cross-repo: `HTTP_CALLS`, `RPC_CALLS`, `MESSAGES` (producer→consumer via Channel), `SHARES_TABLE`, `DEPENDS_ON_ARTIFACT`.
Architecture: `MEMBER_OF` (Repo/Service→BoundedContext→System), `DEPLOYED_AS`, `HAS_ROLE` (Module/Class→LayerRole), `LAYER_DEPENDS` (aggregated), `UPSTREAM_OF` (context map), `VIOLATES` (edge→ArchitectureRule).
History: `CHANGES_WITH` (File↔File, co-change), `SIMILAR_TO` (near-clone).

Every non-containment edge references its `site_id` (byte span, line and column live on the site row) and carries an `observed` flag (0/1). `CONTAINS` is not stored in `edges`; it is `nodes.parent_id`. `HAS_ROLE` is not stored in segments either; `nodes.layer_role` is authoritative and `HAS_ROLE` edges are materialised only in `estate.db`. `DEFINES_ROUTE` points from the handler (`Function`/`Method`) to its `Route` node; `Route` nodes have the handler's file as `file_id`.
