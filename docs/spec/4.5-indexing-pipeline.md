# Indexing pipeline specification

> **Normative.** Changing this document requires a specification change request
> recorded in `docs/plan/ISSUES.md`, and where a stored format is affected, a bump
> of the relevant version constant.
>
> Mirrors section 4.5 of the implementation plan, which is not committed.

## Entry point

The pipeline is one Rust function:

```rust
pdx_core::index::build_segment(IndexRequest) -> Result<SegmentReport>
```

It is used unchanged by the local CLI and by the server job runner.

The pipeline has six stages, which run in the order given below: Discover,
Extract, Resolve, Derive, Write, Publish.

## Stage 1: Discover

Walk the checkout (or working tree), honouring:

- `.gitignore`.
- `.pdxignore`, which uses gitignore syntax.
- Hard-coded excludes: `.git`, `node_modules`, `target`, `build`, `dist`,
  `vendor`. The `vendor` exclude does not apply when `pdx.toml` says
  `[discover] include_vendor = true`.

Rules:

- Symlinks are skipped.
- Files larger than `MAX_FILE_BYTES` (2 MiB) are recorded as `skipped` with
  reason `size`.
- Binary files are recorded as `binary`.
- Language is assigned from Appendix A by extension, then by shebang.
- `pdx.toml [languages] extra = { ".blade.php" = "php" }` extends the language
  map.

## Stage 2: Extract (engine)

For each discovered file that is a candidate with a language in the Language Matrix,
call the engine through the FFI (Appendix D). Every other file is carried forward
with the reason it has no extraction: binary, redacted, skipped for size, of no
language, or skipped for memory (see "Worker and memory limits"). A redacted file is
never opened by Stage 2: not to hash it, not to look for secrets in it, not to
extract or cache it.

### Preparing a file

For each file extracted, in this order:

1. Read its original bytes, after checking, without following a link, that its path
   is still the regular file of the size Stage 1 found. A path that has since become
   missing, a symlink, a directory, another size or binary is a change to the
   checkout, and fails the build.
2. Compute `blob_sha`, the Git blob SHA-1 of the **original** bytes:
   `sha1("blob " ‖ decimal length ‖ 0x00 ‖ bytes)`, written as 40 lower-case hex
   digits, as `git hash-object` computes it.
3. Apply secret normalisation (5.12) to the same buffer, in place (below).
4. Compute `source_digest`, the SHA-256 of the **normalised** bytes: the bytes the
   engine is given, and records in the extraction.
5. Look the extraction up in the cache; extract the normalised bytes on a miss.

`blob_sha` and `source_digest` identify different bytes and are never
interchangeable: `blob_sha` is the file as the repository holds it, `source_digest`
what was extracted. The original bytes reach nothing but `blob_sha`: not the engine,
the cache, a diagnostic or a log.

### Secret normalisation preserves length

Secret normalisation (5.12) masks each secret value its content detectors find,
byte for byte, with ASCII `X`. The normalised bytes have the original's length,
every byte after a secret keeps its offset, and no carriage return or line feed is
masked, so every span, site and identity taken from the normalised source is the
source's own. A key, its separator and quotes, a PEM block's marker lines, line
endings and indentation are kept; only the value's bytes change. `<REDACTED_SECRET>`
is how a masked value is described, not a substitution in the engine's input.
(Specification change 37, `docs/plan/ISSUES.md`.)

What the detectors match, and how a match is masked, is versioned by
`SECRET_DETECTOR_VERSION`; a change to either bumps it.

### Extraction cache

Results are cached by the key:

```
(engine_version, language_matrix_version, secret_policy_digest, language_id, rel_path, blob_sha)
```

- `secret_policy_digest` is the SHA-256 of the compact JSON object
  `{"detector_version":<SECRET_DETECTOR_VERSION>,"patterns":[…]}`, keys in that
  order, the effective secret patterns sorted and each once.
- `language_id` is the matrix language the file was assigned. A repository's
  `[languages]` can assign the same path and bytes another language without any
  version changing.
- `rel_path` is the path the engine is given. Qualified names and the surface depend
  on it, so the same bytes at two paths are two extractions.

Nothing else enters the key: no checkout location, time, machine, worker count or
memory budget. (Specification change 26, `docs/plan/ISSUES.md`.)

An extraction is cached only when it is clean: not truncated by the node budget, and
reporting no work lost (`extraction_lost` of 0). An engine error or crash is never
cached; an extraction the engine returned with status `failed` is cached like any
other clean one. While any engine switch that changes what an extraction contains is
set to any value, the node budget `PDX_ENGINE_WALK_MAX_NODES` among them, no cache is
read or written at all; the switches are named in one place,
`pdx_engine::EXTRACTION_SWITCHES`.

A cached extraction is used only if its entry decodes exactly, with nothing left
over, is of the current cache format, was stored under the same key, and is clean
and taken as the same language, at the same path, from source of the same length and
`source_digest` as the file now normalised. Anything else is a miss: the file is
extracted afresh and the entry replaced. An entry holds the extraction and its
surface, never the source. A cache is an optimisation; a damaged one never changes
what Stage 2 returns.

Cache locations:

- Locally: `~/.cache/pdx/extract/`.
- On the server: the `extract_cache` table in the object store, as one blob per
  key.

Rules:

- A cache hit skips parsing and extraction for the file.
- The typed-resolution pass (Stage 3) walks the parse tree of each file it
  resolves, and re-parses the file when no tree is retained. This is parse-only
  cost (no extraction) and is accepted.
- The cross-file *surface* is cached with the extraction result. It holds the
  file-local extraction facts typed resolution reads, and never state derived from
  other files, such as qualified names resolved through the project. An unchanged
  file may be parsed again but is never extracted again; everything that depends on
  other files is recomputed in every project resolution. Resolving from fresh
  extractions, from cached surfaces, or with files in any order gives the same
  result. (Specification change 18, `docs/plan/ISSUES.md`.)
- Resolution (Stage 3) always runs over the full repository, so that the result
  never depends on the previous build.

### Failures

- The engine refusing a file costs that file, recorded as `failed`.
- Extraction isolated in worker processes: a worker that crashes costs the file it
  crashed on, recorded as `failed` with reason `engine_crash`, and every other file is
  extracted.
- An isolated worker that does not finish an exchange (a batch written and its
  results read) within its timeout, 120 seconds, is killed and reaped and everything
  it sent is discarded. **An isolated-worker timeout is fatal to the build and
  publishes no segment.** It is not `engine_crash`, and no file status records it: a
  wall-clock limit depends on the machine, and a segment must not.
  (Specification change 27, `docs/plan/ISSUES.md`.)
- A worker whose engine cannot start fails the build.

## Stage 3: Resolve

Build the symbol registry for the whole repository: all definitions, all imports,
all class hierarchies.

The registry is built once, from Stage 1's files and Stage 2's extractions, and is
read-only afterwards:

- A definition is identified by its file's path and its index in that file's
  extraction. Definitions are indexed by short name, by exact qualified name and by
  file; a qualified name shared by several definitions (overloads, redeclarations)
  keeps all of them. Names keep the engine's spelling and case.
- Modules follow the language matrix's module rule (Appendix A), from evidence only:
  a declared package or namespace where the extraction carries one
  (`FileExtract::declared_namespace`, or C++'s qualified names), the Python package
  path from the `__init__.py` files discovered, the `go.mod` module path, the crate
  layout under each `Cargo.toml`. Where the evidence is missing, the module is
  absent, never inferred from the directory.
- Each extracted import is kept and classified: internal (one target, or several
  candidates the language's rules do not choose between), external (outside the
  repository), unresolved-internal (it names the repository by a relative path, the
  repository's own module path or alias, and nothing there answers), or unclassified
  (no evidence). A relative import is never external.
- A name is external only when the imports that bind it in a file all lead outside
  the repository and the file does not define it: a name nothing defines and nothing
  imports is not evidence of an external target.
- A base class resolves, in order, as an exact qualified name, a type of that name in
  the same module, a type an import binding it leads to, or the one type of that name
  in the repository; the first that finds any decides, and several are ambiguous. A
  base is external only when the import binding it is.
- Repository metadata (`tsconfig.json`, `package.json`, `go.mod`, `Cargo.toml`) is read
  from candidates only, through the same checks as Stage 2, and is parsed once into
  the metadata the engine's resolver takes; the registry resolves imports with that
  same metadata. (The engine still applies a configuration's aliases to the imports
  of every language: issue 43.)

(Specification changes 40 and 41, `docs/plan/ISSUES.md`: a definition's base classes
and a file's declared namespace cross the engine's interface.)

Then run the following stages, in this order, per call site:

1. Engine typed result. If the engine reports `lsp_typed` with one candidate
   above `TYPED_MIN_SCORE`, the site is resolved as `typed`. Any other engine
   strategy is a hint that seeds, but never restricts, the Rust candidate
   universe.
2. Import-guided.
3. Inheritance-guided.
4. Exact.
5. Scoped.

Restating `4.2-identity-and-bands.md`, which is authoritative for the bands:
each stage names the band it assigns, so a site first resolved to one candidate by
the import-guided stage carries band `import-guided`, by the inheritance-guided
stage `inheritance-guided`, by the exact stage `exact`, and by the scoped stage
`scoped`. Those four bands come from the resolver, never from the engine. See
`4.2-identity-and-bands.md` for what each band means and how they are ordered.

Narrowing semantics:

- The first stage that yields exactly one candidate wins.
- If a stage yields more than one candidate, later stages are still attempted,
  with the candidate set restricted to that set. This is narrowing.
- If no stage narrows to one candidate, the site becomes `candidate` with the
  narrowest set reached.

Bands assigned before or outside the ordered stages:

- Names on the blocklist are `blocked` before any stage runs.
- Names whose only definitions are outside the repository, per import target
  analysis, are `external`.

Only the engine typed result may produce the `typed` band.

## Stage 4: Derive

Derive, from the resolved registry:

- Containment.
- `Module` nodes, from package declarations or from directory structure, per
  Appendix A.
- Routes.
- Tests: `TESTS` edges by naming convention and by framework annotations, per
  Appendix B.5.
- Contracts (4.7.1).
- Layer roles (4.8.3).
- Metrics (4.12.1).
- Coverage rows.

## Stage 5: Write

Insert in sorted order, build FTS, `VACUUM INTO`, compute `content_sha256`, mark
read-only.

## Stage 6: Publish (server only)

Upload to the segment store, insert the `segments` row, and enqueue the `links`,
`layout`, `estate` and `analytics` jobs for the trunk manifest if the segment
belongs to a trunk head.

## Worker and memory limits

- Worker count = min(available CPUs as reported by cgroup quota, `PDX_WORKERS`).
- Memory budget = `PDX_MEM_BUDGET_MB`, or 60% of the cgroup limit.
- The pipeline processes files in batches sized to stay under the budget, and
  reports `degraded` if it had to skip files for memory.

Stage 2 is given the worker count and the budget already resolved. The budget bounds
the source bytes its workers hold at once:

- a file larger than the whole budget is skipped for memory, and the segment is
  `degraded`;
- the workers that run are as many as requested, but no more than can each hold the
  largest remaining file: `workers × largest ≤ budget`, and at least one;
- each worker's share is the budget divided by that count, and batches are filled
  in path order, never past the share;
- a worker holds one batch at a time.

What the engine allocates while it parses and extracts is not known before it does
so, and is not bounded by this; the process's footprint is measured as a whole.

## Degraded status

A segment is `degraded` if either of the following holds:

- `failed + skipped(size) > 5%` of files.
- The engine crashed on any file. The file is recorded as `failed` with reason
  `engine_crash`, and the pipeline continues in a fresh engine context.

The memory case in the previous section also reports `degraded`, and so does an
extraction that was truncated by the node budget or lost work.
