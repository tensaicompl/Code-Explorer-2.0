# Indexing pipeline specification

> **Normative.** Changing this document requires a specification change request
> recorded in `docs/plan/ISSUES.md`, and where a stored format is affected, a bump
> of the relevant version constant.
>
> Mirrors section 4.5 of the implementation plan, which is not committed.

## Entry point

The pipeline is one Rust function:

```rust
pdx_core::index::build_segment(IndexRequest) -> Result<SegmentReport>
```

It is used unchanged by the local CLI and by the server job runner.

`IndexRequest` names the checkout, the repository's identity, URL and name, the
commit, Stage 2's worker and memory limits, the extraction cache and backend, the
destination and an optional progress callback. The limits arrive resolved: the caller
resolves `PDX_WORKERS`, `PDX_MEM_BUDGET_MB` and the cgroup's limits ("Worker and memory
limits"), and `build_segment` does not. Stage 2's engine switches (isolation, the
extraction switches) are Stage 2's and unchanged. The request's meta and destination
are checked before any stage runs.
`SegmentReport` returns the written segment (path, `content_sha256`, size), its status
(`ready` or `degraded`) with every degraded reason, the coverage rows, the
repository's files by status, the files held back for an unportable path, the
segment's row counts and what Stages 2 to 4 reported (extraction statistics, typed
resolution's run health, unstored sites). None of it is written into the segment
unless the schema holds it. A fatal error in any stage returns that stage's error and
publishes nothing. Each stage runs in a `tracing` span (stage names and counts only)
and is reported to the progress callback as started and finished, from the building
thread; neither changes what is built. (P2-10, decisions 33 to 35.)

The pipeline has six stages, which run in the order given below: Discover,
Extract, Resolve, Derive, Write, Publish.

## Stage 1: Discover

Walk the checkout (or working tree), honouring:

- `.gitignore`.
- `.pdxignore`, which uses gitignore syntax.
- Hard-coded excludes: `.git`, `node_modules`, `target`, `build`, `dist`,
  `vendor`. The `vendor` exclude does not apply when `pdx.toml` says
  `[discover] include_vendor = true`.

Rules:

- Symlinks are skipped.
- Files larger than `MAX_FILE_BYTES` (2 MiB) are recorded as `skipped` with
  reason `size`.
- Binary files are recorded as `binary`.
- Language is assigned from Appendix A by extension, then by shebang.
- `pdx.toml [languages] extra = { ".blade.php" = "php" }` extends the language
  map.
- A file whose path is not repository-relative POSIX (a name holding `\`, which
  Windows reads as a separator, or a first name Windows reads as a drive) has no
  identity that is the same on every host. Stage 1 discovers and classifies it like
  any other file (reading it as discovery reads any file); then it is held back, at the
  end of Stage 1: Stages 2 to 5 never process it and no identity is made from its path.
  It is counted as skipped in its language's coverage row and reported with the reason
  `unportable_path` (issue 53).

## Stage 2: Extract (engine)

For each discovered file that is a candidate with a language in the Language Matrix,
call the engine through the FFI (Appendix D). Every other file is carried forward
with the reason it has no extraction: binary, redacted, skipped for size, of no
language, or skipped for memory (see "Worker and memory limits"). A redacted file is
never opened by Stage 2: not to hash it, not to look for secrets in it, not to
extract or cache it.

### Preparing a file

For each file extracted, in this order:

1. Read its original bytes, after checking, without following a link, that its path
   is still the regular file of the size Stage 1 found. A path that has since become
   missing, a symlink, a directory, another size or binary is a change to the
   checkout, and fails the build.
2. Compute `blob_sha`, the Git blob SHA-1 of the **original** bytes:
   `sha1("blob " ‖ decimal length ‖ 0x00 ‖ bytes)`, written as 40 lower-case hex
   digits, as `git hash-object` computes it.
3. Apply secret normalisation (5.12) to the same buffer, in place (below).
4. Compute `source_digest`, the SHA-256 of the **normalised** bytes: the bytes the
   engine is given, and records in the extraction.
5. Look the extraction up in the cache; extract the normalised bytes on a miss.

`blob_sha` and `source_digest` identify different bytes and are never
interchangeable: `blob_sha` is the file as the repository holds it, `source_digest`
what was extracted. The original bytes reach nothing but `blob_sha`: not the engine,
the cache, a diagnostic or a log.

The normalised bytes are all the engine extracts from. An extraction depends on them,
the file's language and `rel_path` alone (and on the engine switches named below,
under which nothing is cached), never on the working directory, another file, the
clock, the time zone or the locale. The engine never reads source from disk: not the
file's own path, and not a header or any other file a directive in it names. C and C++
preprocessing expands only the macros and conditionals the source itself defines; an
`#include` stays an import, its target never opened. Its date and time macros are fixed
values the engine owns: `__DATE__` is `"Jan 01 1970"` and `__TIME__` is `"00:00:00"`.
Engine preprocessing semantics are host-independent: any value the engine predefines or
evaluates is a deterministic project-defined value, never the build machine's ABI or its
C library's. That covers the type sizes of the `sizeof` extension in `#if` (decision 54
lists them), the value of a character constant (one byte is a signed 8-bit char), the
number of a `#line` (decimal, read at a fixed width, at most 4294967295; decision 55),
and `#if` arithmetic: 64-bit two's complement, wrapping modulo 2^64, with integer
literals read at a fixed width and saturating at the 64-bit bounds, a shift of 64 bits
or more giving 0, a negative value shifting right arithmetically, the least value
divided by -1 giving itself (remainder 0), and a negative shift count failing the
condition as a division by zero does (decision 56). So no extraction holds bytes Stage 2
did not normalise, bytes from outside the repository, the time it was made or the
platform it ran on, and the cache key below names every input. (Issues 83 to 87,
decisions 51 and 53 to 56.)

C and C++ preprocessing is bounded by its source, never by the machine: whether it
completes depends on the normalised bytes alone, not on memory, speed, a clock or an
environment variable. A forward jump of more than 4,096 lines within one file (a
`#line`, or a stretch with no tokens) is written into the expanded text as one `#line`
marker, which maps back to its line and is never a fact; a shorter one is padded with a
newline per line. Each file's byte budget is 24 bytes per byte of its source, at least
256 KiB and at most 8 MiB, computed without overflow. Its preprocessing may write at most
that many bytes, padding and markers included; its macro expansion may generate at most
that many bytes of token text and at most 500,000 tokens (temporaries included, the
source's own tokens never), make at most 500,000 expansions (one that creates nothing
included) and nest at most 256 deep; and its `#if` folding may take at most that many
steps. Each ceiling is checked as the work proceeds and stops it at its first step past
the ceiling, never after the result is built. Passing one discards the expansion: the
file is extracted from its normalised source alone, without the macro-expanded pass,
and the extraction reports lost work exactly once, so it is never cached and degrades
its segment. No other status is added. (Issue 87, decision 56.)

Node-type path evidence is bounded per extraction. A site's node-type path (a call's, a
possible callable reference's, a route binding's) is stored only in full; it is never
truncated. At most 1,024 node types may belong to one site's path, and at most 500,000
may be kept across all the site paths of one extraction, every producer of a path
drawing on that one count. Both are checked before the path is allocated. Passing
either is lost work, once; no further site path is computed or kept for the file. Its
sites stay in the extraction: a site lacking its complete node-type path is counted, as
above, and never given a stored identity or row. (Issue 88, decision 57.)

Parsing is safe whatever the source. A grammar scanner keeps its state between tokens
within the parser's fixed state buffer: its state is bounded to what that buffer holds,
a construct that would need more is not opened (the parse recovers, partially), and no
source can make the parser write or read outside that buffer or end the process. This
holds before the depth ceiling below is measured. (Issue 91, decision 60.)

Semantic extraction is admitted by syntax depth. After the parse and before any
semantic pass, the engine measures how deeply the file's syntax tree nests, the root
at depth 1, every node visited once and the measure stopping at the first node past
the ceiling. A tree deeper than 512 is not extracted: the extraction holds no fact,
takes no part in cross-file resolution, and reports lost work exactly once, so it is
never cached and degrades its segment; it is not a parse failure, and no part of the
tree is extracted in its place. The macro-expanded tree of C and C++ is held to the
same depth, and past it the expanded pass alone is skipped, losing work once. The
ceiling is one for every language, and depends on no time, machine or setting: the
measure inspects every node whatever the node budget (`PDX_ENGINE_WALK_MAX_NODES`), which
bounds the extraction walk alone. (Issue 89, decision 58.) Within the admitted depth,
classifying a usage asks about its ancestors through the extraction walk's own path, so
that work is linear in the tree, never in its depth squared. (Issue 90, decision 59.)

Text an extraction takes from the file is held once: as the source's bytes, with each
fact holding a bounded reference to them, never a copy of its own. The rules are:

- Text that is exactly one contiguous run of the normalised source the engine was given
  (a callee as the source spells it at its call, an argument's expression, a usage's
  name, a Python attribute chain included, a route's declaring node, a definition's
  parameter list) is stored as that run's byte range. A range is the text itself: nothing is trimmed, unquoted or
  rewritten inside it.
- Ranges refer to the normalised extraction input, and to nothing else.
- Text the engine assembled, rewrote or shortened, and text it read in C and C++
  macro-expanded source, which the caller never sees, is stored as owned text. No range
  points into expanded text.
- A definition's qualified name is logically unchanged, byte for byte, but may be held
  by its relation to an earlier definition's: a member of it (that name, `.`, the
  definition's own name), its name extended by a rest, or a prefix of its name ending
  before a `.` that definition adds, then a rest (names that share a prefix no
  definition is, as C++ functions in nested namespaces do). Spelled out, it is exactly
  the whole name. A consumer keeps it so until a layer stores whole names, as a node's
  row does.
- Every hash and identity computed from a qualified name or a text uses exactly the
  bytes of the whole name or text, so node and site identities do not depend on how
  either is held.
- The extraction cache stores ranges, never another copy of the source. A hit binds its
  ranges to the verified current normalised source: of the entry's length and digest,
  every range within it, or the entry is a miss, never clamped or read unchecked.
- An isolated worker answers with ranges of the source it was sent, never the source
  again, and the parent binds them to that source the same way.

So what an extraction retains grows with its source and its facts, not with how deeply
its text nests. (Issue 90, decision 61.)

### Secret normalisation preserves length

Secret normalisation (5.12) masks each secret value its content detectors find,
byte for byte, with ASCII `X`. The normalised bytes have the original's length,
every byte after a secret keeps its offset, and no carriage return or line feed is
masked, so every span, site and identity taken from the normalised source is the
source's own. A key, its separator and quotes, a PEM block's marker lines, line
endings and indentation are kept; only the value's bytes change. `<REDACTED_SECRET>`
is how a masked value is described, not a substitution in the engine's input.
(Specification change 37, `docs/plan/ISSUES.md`.)

What the detectors match, and how a match is masked, is versioned by
`SECRET_DETECTOR_VERSION`; a change to either bumps it (4 since issue 73).

### One pass over the original bytes

Every content detector reads the file's original bytes. The ranges they find are
merged, and the merged ranges are masked once; no detector ever reads a masked byte.
Normalising normalised bytes changes nothing, and that holds because no detector can
find in masked output a secret it did not find in the source, never because the
output is rescanned until it stops changing. A rescan would read masks as source and
could find secrets the source does not hold. A match that another detector's mask
could complete must therefore be found on the original bytes. (Specification changes
44 and 72, `docs/plan/ISSUES.md`.)

### URI passwords

The URI password detector finds the password of `scheme://user:password@` and masks
the password alone: the scheme, `://`, the user, `:`, `@` and the host stay. What
stands before `://` is either

- **a scheme-shaped substring.** The scheme itself follows URI scheme syntax: a letter,
  then letters, digits, `+`, `-` and `.`. For secret detection it is recognised at the
  start of the input or immediately after any byte that is not an ASCII letter or
  digit: a space, `_`, `-`, `+`, `.`, `/`, `:`, `=`, `~`, a quote, a bracket, any other
  punctuation, or a byte outside ASCII. That byte is never part of the secret. The
  boundary is deliberately conservative, so punctuation before a connection string
  never stops its password being masked: in `1.mysql://u:p@h` the substring
  `mysql://u:p@h` is recognised after `.`, though `1.mysql` is no scheme. After a
  letter or a digit no scheme starts (`9mysql://u:p@h` holds no URI password), and
  since the mask `X` is a letter, masking never opens a boundary; or
- **a bearer token**, exactly as the bearer detector finds one (`Bearer`, spaces or
  tabs, the token). This is the cross-detector fixed-point rule: masked, a bearer
  token is a run of `X`, which is a scheme, so the password after it must be found on
  the original bytes, whatever the token ends with (`Bearer 0000000000000000://…`,
  `Bearer <token>_://…`).

This is a secret detector, not a URI parser, and makes no claim that what it matches
is a valid URI. Secret prevention prefers masking a credential-shaped substring to
leaking a real password because the punctuation around it makes the whole token
formally unusual. The detector finds everything detector version 2 found, whose
regex word boundary already allowed a scheme after punctuation, and more (`_`, the
bearer rule); a later version may find more, but never loses a password an earlier
one masked without an approved specification change. (Specification changes 72 and
73, decisions 42 and 43.)

### Extraction cache

Results are cached by the key:

```
(engine_version, language_matrix_version, secret_policy_digest, language_id, rel_path, blob_sha)
```

- `secret_policy_digest` is the SHA-256 of the compact JSON object
  `{"detector_version":<SECRET_DETECTOR_VERSION>,"patterns":[…]}`, keys in that
  order, the effective secret patterns sorted and each once.
- `language_id` is the matrix language the file was assigned. A repository's
  `[languages]` can assign the same path and bytes another language without any
  version changing.
- `rel_path` is the path the engine is given. Qualified names and the surface depend
  on it, so the same bytes at two paths are two extractions.

Nothing else enters the key: no checkout location, time, machine, worker count or
memory budget. (Specification change 26, `docs/plan/ISSUES.md`.)

An extraction is cached only when it is clean: not truncated by the node budget, and
reporting no work lost (`extraction_lost` of 0). An engine error or crash is never
cached; an extraction the engine returned with status `failed` is cached like any
other clean one. While any engine switch that changes what an extraction contains is
set to any value, the node budget `PDX_ENGINE_WALK_MAX_NODES` among them, no cache is
read or written at all; the switches are named in one place,
`pdx_engine::EXTRACTION_SWITCHES`.

A cached extraction is used only if its entry decodes exactly, with nothing left
over, is of the current cache format, was stored under the same key, and is clean
and taken as the same language, at the same path, from source of the same length and
`source_digest` as the file now normalised, and its every text range lies within that
source. Anything else is a miss: the file is extracted afresh and the entry replaced.
An entry holds the extraction, its text as ranges of the source (above), and its
surface, never the source; a hit is bound to the file's source as Stage 2 has just read
and normalised it. A cache is an optimisation; a damaged one never changes what Stage 2
returns.

Cache locations:

- Locally: `~/.cache/pdx/extract/`.
- On the server: the `extract_cache` table in the object store, as one blob per
  key.

Rules:

- A cache hit skips parsing and extraction for the file.
- The typed-resolution pass (Stage 3) walks the parse tree of each file it
  resolves, and re-parses the file when no tree is retained. This is parse-only
  cost (no extraction) and is accepted.
- The cross-file *surface* is cached with the extraction result. It holds the
  file-local extraction facts typed resolution reads, and never state derived from
  other files, such as qualified names resolved through the project. An unchanged
  file may be parsed again but is never extracted again; everything that depends on
  other files is recomputed in every project resolution. Resolving from fresh
  extractions, from cached surfaces, or with files in any order gives the same
  result. (Specification change 18, `docs/plan/ISSUES.md`.)
- Resolution (Stage 3) always runs over the full repository, so that the result
  never depends on the previous build.

### Failures

- The engine refusing a file costs that file, recorded as `failed`.
- Extraction isolated in worker processes: a worker that crashes costs the file it
  crashed on, recorded as `failed` with reason `engine_crash`, and every other file is
  extracted.
- An isolated worker that does not finish an exchange (a batch written and its
  results read) within its timeout, 120 seconds, is killed and reaped and everything
  it sent is discarded. **An isolated-worker timeout is fatal to the build and
  publishes no segment.** It is not `engine_crash`, and no file status records it: a
  wall-clock limit depends on the machine, and a segment must not.
  (Specification change 27, `docs/plan/ISSUES.md`.)
- A worker whose engine cannot start fails the build.

## Stage 3: Resolve

Build the symbol registry for the whole repository: all definitions, all imports,
all class hierarchies.

The registry is built once, from Stage 1's files and Stage 2's extractions, and is
read-only afterwards:

- A definition is identified by its file's path and its index in that file's
  extraction. Definitions are indexed by short name, by exact qualified name and by
  file; a qualified name shared by several definitions (overloads, redeclarations)
  keeps all of them. Names keep the engine's spelling and case.
- Modules follow the language matrix's module rule (Appendix A), from evidence only:
  a declared package or namespace where the extraction carries one
  (`FileExtract::declared_namespace`, or C++'s qualified names), the Python package
  path from the `__init__.py` files discovered, the `go.mod` module path, the crate
  layout under each `Cargo.toml`. Where the evidence is missing, the module is
  absent, never inferred from the directory.
- Each extracted import is kept and classified: internal (one target, or several
  candidates the language's rules do not choose between), external (outside the
  repository), unresolved-internal (it names the repository by a relative path, the
  repository's own module path or alias, and nothing there answers), or unclassified
  (no evidence). A relative import is never external.
- A name is external only when the imports that bind it in a file all lead outside
  the repository and the file does not define it: a name nothing defines and nothing
  imports is not evidence of an external target. In Rust, the crates of the standard
  distribution and the dependencies a crate's manifest declares with no repository
  path bind their names in each of its files as such an import would (the extern
  prelude), for a path that starts with one (issue 104).
- A base class resolves, in order, as an exact qualified name, a type of that name in
  the same module, a type an import binding it leads to, or the one type of that name
  in the repository; the first that finds any decides, and several are ambiguous. A
  base is external only when the import binding it is.
- Repository metadata (`tsconfig.json`, `package.json`, `go.mod`, `Cargo.toml`) is read
  from candidates only, through the same checks as Stage 2, and is parsed once into
  the metadata the engine's resolver takes; the registry resolves imports with that
  same metadata. A configuration's path aliases apply to TypeScript and JavaScript
  imports only, in the registry and in the engine alike (issue 43,
  `engine/patches/0009-script-path-aliases-only.patch`).
- A static import (`import static q.Util.helper`) names a member of a type: it is
  internal when a declared package `q` of the repository defines the type `Util`.
- Rust's `impl Trait for Type` relations (`FileExtract::impl_traits`, empty blocks
  included) are resolved as bases are: the type by its recorded qualified name, else
  by its name; the trait by its name. A relation counts only when both are exactly one
  type of the repository. The engine does not record supertraits, so none is followed
  or guessed.

(Specification changes 40, 41 and 42, `docs/plan/ISSUES.md`: a definition's base
classes, a file's declared namespace and its `impl Trait for Type` relations cross the
engine's interface.)

Then run the following stages, in this order, per call site:

1. Engine typed result. If the engine reports `lsp_typed` with one candidate
   above `TYPED_MIN_SCORE`, the site is resolved as `typed`. Any other engine
   strategy is a hint that seeds, but never restricts, the Rust candidate
   universe.
2. Import-guided.
3. Inheritance-guided.
4. Exact.
5. Scoped.

Restating `4.2-identity-and-bands.md`, which is authoritative for the bands:
each stage names the band it assigns, so a site first resolved to one candidate by
the import-guided stage carries band `import-guided`, by the inheritance-guided
stage `inheritance-guided`, by the exact stage `exact`, and by the scoped stage
`scoped`. Those four bands come from the resolver, never from the engine. See
`4.2-identity-and-bands.md` for what each band means and how they are ordered.

Narrowing semantics:

- The first stage that yields exactly one candidate wins.
- If a stage yields more than one candidate, later stages are still attempted,
  with the candidate set restricted to that set. This is narrowing.
- If no stage narrows to one candidate, the site becomes `candidate` with the
  narrowest set reached.

Bands assigned before or outside the ordered stages:

- A qualifying unique typed answer is accepted first. If no such typed answer
  exists, a blocklisted generic name is `blocked` before any name-based resolver
  stage runs (issue 103, decision 65).
- Names whose only definitions are outside the repository, per import target
  analysis, are `external`.

Only the engine typed result may produce the `typed` band.

### Precedence and evidence

Typed resolution runs over the whole current repository on every build: every
extracted file, in path order, its source read again through Stage 2's checks and
refused if it is not the source Stage 2 extracted, with the registry's metadata. No
answer is cached or carried over from another build. A run that completes degraded
is reported with its health; the absence of an answer is never evidence.

Each site is then settled in this order of precedence:

1. A qualifying unique typed answer is accepted first: `typed` when the engine's
   answer for the site is `lsp_typed` with one candidate and a score from
   `TYPED_MIN_SCORE` to 1, and its file and qualified name are exactly one definition
   of the repository, whatever the callee's name (issue 103, decision 65).
2. If no such typed answer exists, the blocklist (Appendix B.4, its 57 names and the
   documented additions per language): a blocklisted generic name is `blocked` before
   any name-based resolver stage runs. An engine hint never passes it.
3. The engine's answer for the site, at most one (two different answers for one site
   fail the stage). A qualifying answer whose file and qualified name are several
   definitions or none leaves its definitions as candidates. A target in no file of
   the project (a built-in) is `external`, and the name is not resolved in the
   repository (issue 45). The engine's score, strategy and candidate count are kept
   verbatim either way.
4. Bindings that stop resolution by name. A name the source binds locally
   (`BLOCKED`, `BLOCKED_LOCALLY`, `LOCALLY_BOUND`) is `unresolved`. A name, or a
   receiver's first name, that the file binds only through imports of external
   packages is `external`: no definition elsewhere in the repository is viable for
   it. So is a Rust path (`multer::parse_boundary`, no method called on a value)
   whose first name nothing in the file binds and the extern prelude binds to an
   external crate (issue 104). A member call whose receiver the extractor could not
   tie to anything (`UNRESOLVED_MEMBER`) is not resolved by its name alone: exact and
   scoped do not run, and import-guided only when the receiver is a name the file
   imports from the repository.
5. The Rust stages over the candidates: the definitions a call can invoke (functions,
   methods, constructors, classes, structs, macros) of the caller's language family
   (the language; TypeScript and JavaScript; C and C++) by the callee's short name, by
   its whole text as a qualified name, through the file's imports under the name they
   bind them to, and any the engine's answer names.
   - Import-guided: a candidate the file's imports make visible: through an import
     binding the callee's name (as the member it imports, aliased or not), through
     one binding no name (a wildcard, namespace or include, the source paired with an
     included header too) for a definition at the top of its file unless the call is
     inside a type in a language where a bare name there is a member, or, for a
     receiver, through an import binding the receiver as the module or type it names.
   - Inheritance-guided: for a receiver that is the current object or type (`this`,
     `self`, `$this`, `Self`, `cls`, or a bare name in Java, Kotlin, C#, C++, Scala,
     Groovy, Swift or Ruby) the candidates declared in the caller's type's hierarchy,
     and for `super`, `super()`, `base` or `parent` in its bases only. The hierarchy is
     the type, its internal bases and, for Rust, the internal traits it implements
     directly; where no type on the way has more than one, the nearest level declaring
     a candidate decides. Any other receiver proves no type here.
   - Exact: the candidate, when it is the one definition of the callee's name in the
     repository. Several definitions of the name are evidence for none of them, so
     exact never narrows to several.
   - Scoped: the candidates in the caller's module (the caller definition's, else the
     file's when it has exactly one). A directory is a module only where Appendix A
     says so.
6. `candidate` with the narrowest set reached, or `unresolved` when there is none.

A site that is only a question for typed resolution (`typed_only`), a callable passed
as a value (`is_reference`), and a site typed resolution found past the extraction's
calls are call sites only when step 1 settles them as `typed` or step 3 as `external`;
otherwise they are reported as unconfirmed and never resolved by name.

## Stage 4: Derive

Derive, from the resolved registry:

- Containment.
- `Module` nodes, from package declarations or from directory structure, per
  Appendix A.
- Routes.
- Tests: `TESTS` edges by naming convention and by framework annotations, per
  Appendix B.5.
- Contracts (4.7.1).
- Layer roles (4.8.3).
- Metrics (4.12.1).
- Coverage rows.

The stage is where facts first get persistent identities (4.2.1), from the fields 4.2.1
names and nothing else: no line, offset, call index, insertion order or checkout
location. Every path in an identity is repository-relative POSIX; a host-native path
(`\`, a drive letter, an absolute path, `.` or `..`) stops the stage rather than
become one. Its output is sorted by stored identity (files by path, nodes, sites and
edges by id, candidate rows by site) and is the same whatever order discovery,
extraction or resolution produced their facts in.

Containment, routes, tests and entry points (P2-07):

- **Containment.** A `Repo` node; a `Folder` node for every directory a discovered
  path implies; a `File` node and a file record for every discovered file, whatever
  became of it. A file's status is what Stage 2 did: `parsed` or `partial` by the
  engine's report, `failed` for a parse failure, an engine error or a crash (the
  reason says which), `skipped` for size, memory or no language, `binary` and
  `redacted` as discovery found them. Its `blob_sha` and `line_count` are the ones
  Stage 2 took from the bytes it read; a file never read has neither.
- **Definitions.** One node per extracted definition, its kind the definition's
  (`Class`, `Interface`, `Enum`, `Struct`, `Trait`, `TypeAlias`, `Function`,
  `Method`, `Constructor`, `Field`, `Variable`, `Macro`, and `Module` for a namespace
  block the engine extracts), parented to the definition enclosing it or else to its
  file. The engine's file-level module definition is the file node, never a second
  node. One map from each definition to its node serves every part of the stage.
  Props: `engine_kind`, `visibility` (Go and Python only, where the engine's is
  evidence: issue 68), `is_test`, `is_entry_point`, and `module`.
- **Modules.** One `Module` node per module of the registry, in a language whose
  module is not the file itself, keyed as 4.2.1 says (issue 48). A module in one
  file has that file as `file_id` and parent. A module spanning files has no
  `file_id`, its member paths sorted in `props.files`, and the nearest folder holding
  them all (or the repository) as parent. Symbols keep their physical parents; their
  module is `props.module`.
- **Calls** (issue 49). Each Stage 3 resolution becomes a site (`call`, or
  `reference` for a callable passed as a value) in the definition the engine
  attributes it to: the nearest enclosing definition it extracted. A nested callable
  the engine does not extract keeps its own lexical scope for bindings and
  shadowing, but owns no site; its sites belong to the nearest extracted definition
  around it, or to the file (issue 75, decision 47). The callable a call is lexically
  found in and the definition that owns its site are separate facts. The first is a
  name, the engine's own canonical spelling, which typed resolution joins its answers
  on. The second is tied to the declaration's occurrence in the source, so it holds
  when the two names differ (issue 76, decision 48). A site with no position in the
  file is never owned: its caller is resolution context only. A drawn band adds a `CALLS` or `CALL_REFERENCE` edge from that
  definition (or from the file, at file scope) to the target, with the engine's score,
  strategy and candidate count copied unchanged; any other band adds a candidate row
  with the candidates' nodes, sorted, once each, and the same engine numbers. Stage
  3's unconfirmed sites are carried for counting and never become rows. A resolution
  whose site has no position in the file or no node-type path is counted and never
  stored.
- **Tests.** A file is a test file by its language's rules (Appendix A, issue 31): a
  `.test` or `.spec` stem on any of the language's own extensions (JavaScript takes
  TypeScript's convention on its own extensions), a file-name prefix or suffix, or a
  directory pattern matched at any depth on whole path components, a pattern of
  several components matching consecutive ones, and `test*` any component beginning
  `test`, case-sensitively. A definition is a test only on evidence about itself, as
  its framework decides: a `JUnit` or `TestNG` annotation; an `xUnit`, `NUnit` or
  `MSTest` attribute; Rust's `#[test]`; pytest's and unittest's `test` prefix in a
  test file, at the top of a module or in a test class; Go's `TestXxx` in a
  `_test.go` file; `PHPUnit`'s `test` prefix or `@test` in a test file; a `GoogleTest`
  macro's definition. A test callable is a `Test` node in place of its `Function` or
  `Method` node, its declared kind in `props.declared_kind`. Every drawn call a test
  makes keeps its `CALLS` edge and gains a `TESTS` edge beside it, with the same
  target, band, site and engine numbers. A helper in a test file is not a test.
- **Routes.** For Spring and JAX-RS (mapping annotations), `FastAPI`, Flask and Django
  REST framework (route decorators) and Express (`<router>.<method>(path, …, handler)`
  in a file that imports `express`): a `Route` node per binding, in the handler's file,
  keyed as 4.2.1 says, and a `DEFINES_ROUTE` edge from the handler at the binding's
  `route` site. The engine reports every binding a declaration makes, each with the
  declaring node's position and node-type path (issue 54): an annotation listing
  several paths or methods is one binding per method and path, joined to the class's
  own mapping; a path or method that is not a literal is no binding. One declaration
  is one site, shared by the edges of all its bindings. An Express handler is the
  definition its argument resolves to, or the one callable of that name in the same
  file. A binding with no site in the source, and an inline Express handler, give no
  route and no edge, and are reported.
- **Entry points** (Appendix B.2), as `props.is_entry_point`, decided from evidence of
  B.2's categories (issue 55): every test and route handler; a program's `main` by its
  language's convention (Java's and Groovy's `main(String[])`, Scala's, Kotlin's,
  C#'s `Main`, C's, C++'s in the global namespace, Go's `func main()`, Rust's `fn
  main()` in a binary's root); a class annotated `@SpringBootApplication`; a
  module-level `FastAPI` or Flask application; the definition calling `listen` on an
  Express application or `NestFactory.create`; an ASP.NET `Program.cs` with top-level
  statements. The engine's own entry-point flag, which it sets on every exported
  JavaScript or TypeScript declaration, is kept as `props.engine_entry_point` and is
  not one of these. Go's package clause is not extracted, so a `func main()` outside
  package `main` is taken for one. Command-line handlers and names alone (`run`,
  `start`) are not entry points.

Contracts (P2-08), last, reading the nodes above:

- **Contracts** (4.7.1 and its clarifications). One `contracts` row per contract the
  repository provides or consumes, sorted by `contract_id`, made by one accumulator
  from what each source observed: OpenAPI and Swagger documents, the `Route` nodes
  above, the framework declarations no `Route` node is made for (`NestJS`, ASP.NET,
  Hono, `net/http`, gin, echo, axum, actix-web), HTTP client calls, protobuf services
  and their stub calls, broker client calls, the engine's channel facts a client call
  confirms, listener annotations, `AsyncAPI` documents, DDL, changelogs, ORM mappings,
  SQL literals and build manifests (4.7.1's coverage: issue 62). Every
  document is read as Stage 2 reads a file (a redacted, binary or oversized file never;
  an extracted one must still be the bytes Stage 2 identified, or the stage stops),
  and only literals and single configuration values are used. A document no parser
  can read is reported (`Diagnostics::contracts`) and gives no contract. Contracts add
  no node and no edge to the graph (issue 59).

Layer roles and metrics (P2-09), last, once the graph above is complete:

- **Layer roles** (4.8.3 and its clarifications). Every `Module` and `Class` node gets
  one `layer_role`, `unknown` included; no other node has one. The repository's
  `pdx.toml [layers]` rules decide first, then framework evidence with its provenance,
  then path conventions. No `HAS_ROLE` or `LAYER_DEPENDS` edge is made here.
- **Metrics** (4.12.1 and its clarifications). One `metrics` row per symbol and
  metric, sorted by node then metric, every value finite, a second value refused. A
  symbol is an extracted definition's node, but not the file-level module, which is
  its file, nor an inline module. Every symbol has `loc`, `fan_in`, `fan_out` and
  `importance`. A callable also has `cyclomatic`, `cognitive`, `loop_depth` and
  `transitive_loop_depth`. A symbol in a cycle of drawn calls has
  `props.recursive = true`. A missing fact gives no row and a diagnostic
  (`Diagnostics::metrics`), never a made-up value.

Coverage rows (P2-10, 4.3's `coverage`; decision 33), one per language with a file:

- **Files.** `files` is every file of the language, held-back files included;
  `parsed`, `partial`, `failed` and `skipped` follow the file's status above. A binary
  or redacted file is in `files` only: nothing was attempted.
- **Symbols.** The extracted definitions, each once: not the engine's file-level
  module (the file), and a test callable once whatever its node's kind.
- **Call sites.** Every call site Stage 3 resolved, once, in its file's language,
  under its band: Stage 3's report is the truth, so a site Stage 4 could not store
  still counts and an unconfirmed site never does. `by_band` holds all eleven bands
  and sums to `call_sites`. `observed_links` is 0.

## Stage 5: Write

Insert in sorted order, build FTS, `VACUUM INTO`, compute `content_sha256`, mark
read-only. Stage 5 writes Stage 4's rows and the coverage through the segment writer;
a structural segment's `evidence` and `semantic_occurrences` are empty. The writer
refuses a coverage row whose bands do not sum to its call sites.

## Stage 6: Publish (server only)

Upload to the segment store, insert the `segments` row, and enqueue the `links`,
`layout`, `estate` and `analytics` jobs for the trunk manifest if the segment
belongs to a trunk head.

## Worker and memory limits

- Worker count = min(available CPUs as reported by cgroup quota, `PDX_WORKERS`).
- Memory budget = `PDX_MEM_BUDGET_MB`, or 60% of the cgroup limit.
- The pipeline processes files in batches sized to stay under the budget, and
  reports `degraded` if it had to skip files for memory.

(P2-11, decision 37.) The local binary resolves them: workers are the least of the
processors available, the cgroup's CPU quota (`quota / period`, rounded down, at least
one) and `PDX_WORKERS`, at least one; the memory budget is `PDX_MEM_BUDGET_MB` MiB, else
60% of the cgroup's memory limit (rounded down, in integers), else
`DEFAULT_MEMORY_BUDGET_BYTES` (512 MiB) on every platform. A cgroup limit is the
tightest of the process's group and its ancestors. A `PDX_WORKERS` or
`PDX_MEM_BUDGET_MB` that is not a positive whole number fails the command.

Stage 2 is given the worker count and the budget already resolved, by the caller of
`build_segment` (the CLI or the server job), never by the pipeline itself. The budget
bounds the source bytes its workers hold at once:

- a file larger than the whole budget is skipped for memory, and the segment is
  `degraded`;
- the workers that run are as many as requested, but no more than can each hold the
  largest remaining file: `workers × largest ≤ budget`, and at least one;
- each worker's share is the budget divided by that count, and batches are filled
  in path order, never past the share;
- a worker holds one batch at a time.

What the engine allocates while it parses and extracts is not known before it does
so, and is not bounded by this; the process's footprint is measured as a whole.

## Degraded status

A segment is `degraded` if either of the following holds:

- `failed + skipped(size) > 5%` of files.
- The engine crashed on any file. The file is recorded as `failed` with reason
  `engine_crash`, and the pipeline continues in a fresh engine context.

The memory case in the previous section also reports `degraded`, and so does an
extraction that was truncated by the node budget or lost work.

Lost work is work an engine budget or a failed allocation cut short (issue 21). The C
and C++ expression type evaluator's step budget is per file and derived only from the
length of the source text it evaluates (the file, or its macro-expanded text): 10,000
steps per started 32 KiB, at least 10,000 and at most 320,000. A larger file gets
proportionally more work, and every input a finite ceiling. Exhausting it remains lost
work. (Specification change 74, decision 45.) Passing one of the preprocessing ceilings
above is lost work too, counted once per file. (Issue 87, decision 56.)

(P2-10, decision 34.) The status is decided once, from every file's outcome. "Of
files" is every file of the repository, binary, redacted and held-back files
included; "more than 5%" is strict and computed in integers (`20 × (failed +
skipped(size)) > files`), so exactly 5% is not degraded. `failed` is a parse failure,
an engine error or a crash. A file's status is the engine's report (issue 57): a
`partial` file is no reason, nor is a file of no language, binary, redacted or held
back, nor typed resolution's run health (reported, not a reason). A worker timeout
stays fatal.
