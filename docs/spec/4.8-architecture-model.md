## 4.8 Architecture model L0 to L5

The estate is modelled at six levels. Each level fixes its node kinds, the sources
it is built from, and the determinism it carries.

| Level | Nodes | Source | Determinism |
|---|---|---|---|
| L0 System | `System` | `pdx-arch.yaml` at estate level (admin-managed, stored in `settings`) or Backstage `catalog-info.yaml` `kind: System` found in repos | annotated |
| L1 Context | `BoundedContext` | `pdx-arch.yaml`; Backstage `Domain`; jMolecules `@BoundedContext`; else one context per repo named after the repo | annotated / derived |
| L2 Container | `Service`, `Library`, `Database`, `Broker`, `Frontend`, `BatchJob`, `Deployment` | a repository may contain 0..N L2 components; detection order: (1) explicit `pdx-arch.yaml`/Backstage mapping; (2) each `Dockerfile` (or K8s workload image built from the repo) defines one component rooted at the Dockerfile's build context; (3) each executable entry-point cluster (a `main`/bootstrap with its reachable modules) defines one component; (4) otherwise one `Library` per build artifact; a component that provides ≥1 `ApiContract`/`RpcMethod` is a `Service`, one whose entry point is a scheduled job is a `BatchJob`, one that only serves static assets is a `Frontend`; `Database` per distinct datasource identity; `Broker` per broker identity; `Deployment` per K8s `Deployment`/`StatefulSet`/`CronJob` `Resource` linked by image name | derived |
| L3 Component | `LayerRole` assignment on `Module`/`Class` | 4.8.3 | derived + rule-checked |
| L4 Module | `Module` | engine | precise |
| L5 Symbol | all symbol kinds | engine | per-edge band |

### Level 2 detection order

A repository may contain 0..N L2 components. Detection runs in this order, and the
first rule that produces a component for a given root wins:

1. Explicit `pdx-arch.yaml`/Backstage mapping.
2. Each `Dockerfile` (or K8s workload image built from the repo) defines one
   component rooted at the Dockerfile's build context.
3. Each executable entry-point cluster (a `main`/bootstrap with its reachable
   modules) defines one component.
4. Otherwise one `Library` per build artifact.

Component kind is then fixed by these rules:

- A component that provides ≥1 `ApiContract`/`RpcMethod` is a `Service`.
- A component whose entry point is a scheduled job is a `BatchJob`.
- A component that only serves static assets is a `Frontend`.
- `Database` per distinct datasource identity.
- `Broker` per broker identity.
- `Deployment` per K8s `Deployment`/`StatefulSet`/`CronJob` `Resource` linked by
  image name.

## 4.8.1 `pdx-arch.yaml` (estate-level, optional)

```yaml
version: 1
systems:
  - id: atm-core
    name: ATM Core
    contexts: [flight-data, surveillance]
contexts:
  - id: flight-data
    name: Flight Data
    repos: ["group/fdp-service", "group/fdp-api"]     # host project paths, matched to repos.host_project_key
    identity:                                            # 4.7.1 namespace identity, per repo (optional)
      "group/fdp-service": { hostnames: ["fdp-service", "fdp.internal.example"], brokers: ["kafka-main"], datasources: ["pg-fdp"] }
    upstream_of: [surveillance]                         # context map
layer_rules:                                             # 4.8.3 overrides; optional
  - repo: "group/fdp-service"
    match: { path_glob: "src/main/java/**/web/**" }
    role: api
architecture_rules:                                      # 4.12.2
  - id: no-api-to-persistence
    forbid: { from_role: api, to_role: persistence, edge: CALLS }
  - id: no-cycles-between-contexts
    forbid_cycles: { level: context }
```

Changes to this file are recorded as `annotations` rows with `origin = 'file'` and
are applied on the next `estate` job.

## 4.8.2 Backstage import

If a repo contains `catalog-info.yaml`, `kind: Component` maps to the repo's
`Service`/`Library` (`spec.type` → `service|library|website|…`), `spec.system` →
`System`, `spec.owner` → `props.owner`, `providesApis`/`consumesApis` →
`ApiContract` keys when the API entity has an OpenAPI definition.

## 4.8.3 Layer-role assignment (deterministic)

Precedence, first match wins, per `Module`/`Class`:

1. `layer_rules` in `pdx-arch.yaml` or repo `pdx.toml [layers]` (same schema).
2. Framework annotations: Spring `@RestController|@Controller` → `api`;
   `@Service` → `service`; `@Repository`, JPA `@Entity` with repository usage →
   `persistence`; jMolecules `@Port`/`@Adapter` → `port`/`adapter`; NestJS
   `@Controller` → `api`, `@Injectable` in `*.service.ts` → `service`;
   FastAPI/Flask decorated handlers → `api`; SQLAlchemy models → `persistence`;
   ASP.NET `[ApiController]` → `api`, `DbContext` → `persistence`.
3. Path conventions: any path segment in
   `{controllers, controller, api, rest, web, handlers, routes, endpoints}` →
   `api`; `{services, service, application, usecases, use_cases}` → `service`;
   `{domain, model, models, entities, core}` → `domain`;
   `{repository, repositories, persistence, dao, db, storage, migrations}` →
   `persistence`;
   `{adapters, adapter, clients, client, gateway, gateways, infra, infrastructure}`
   → `adapter`; `{ports, port}` → `port`; test roots → `test`.
4. Otherwise `unknown`.

`LAYER_DEPENDS` edges are aggregated `CALLS`/`USES_TYPE`/`IMPORTS` between roles
inside a `Service`, weighted by count, `worst_band` = lowest band among
constituents.

### Clarifications (P2-09)

A repository's Stage 4 assigns roles from its own `pdx.toml [layers]` (P2-09). The
estate model (P6-02) applies `pdx-arch.yaml`'s `layer_rules` and materialises
`HAS_ROLE` and `LAYER_DEPENDS`. `nodes.layer_role` is the segment's record:
`unknown` when no tier decides, and absent only on a node that is not a `Module` or
`Class`. These read what 4.8.3 leaves open (`docs/plan/DECISIONS.md`, decisions 26,
27 and 31):

- **Configuration.** Rules are tried in order and the first match wins, a configured
  `unknown` included. Globs are `globset`'s, as the configuration is validated,
  matched case-sensitively against repository-relative POSIX paths. A class, and a
  module the engine extracts as a definition, is matched by its file. A semantic
  module is matched by its member files, sorted, and the first rule matching any of
  them wins.
- **Framework evidence** needs provenance, never a name alone. A bare annotation
  counts when the file imports that name from the framework, or when a wildcard or
  C# `using` brings the package in and the repository declares no type of that name.
  A qualified annotation counts only when qualified by the framework's package.
  - Spring and jMolecules: annotations, in Java and Kotlin.
  - `NestJS`: decorators, `@Injectable` only in `*.service.ts`.
  - ASP.NET: `[ApiController]`.
  - Entity Framework: a base `DbContext` that is no type of the repository.
  - `FastAPI` and Flask: a `Route` node of that framework, giving its handler's class
    `api`, or else the handler's module (never the handler, never a file).
  - `SQLAlchemy`: a class owning a table contract with `SQLAlchemy`'s evidence.
  - JPA `@Entity` "with repository usage" needs a repository's base-class type
    argument, which no repository's facts keep (issue 64): until they do, the rule
    never decides and a path rule may.
  - When several rules match, the first in the order above decides.
- **Path conventions.** Whole segments only, case-sensitively. The sets are tried in
  the order listed: `api`, `service`, `domain`, `persistence`, `adapter`, `port`, then
  `test` for a test path by its language's rules (issue 31). A module whose member
  files give different roles is `unknown` at this tier.

## 4.8.4 Annotations and proposals

LLM-generated proposals for names, context membership or role overrides are
**never** written into segments. They enter `annotations` with
`origin = 'proposal'`, `status = 'proposed'`, and are applied by the `estate` job
only when `status = 'approved'` by a principal with role `maintainer` or `admin`.
PDX 2.0 ships the annotation store and review API; the proposal generator itself
is out of scope for 2.0 (Part 1.4) and the API is designed for it.
