## 4.9.1 Surfaces

There are exactly two surfaces. Both expose the same tool names (4.9.2).

**Remote.** `pdx server` exposes `POST /mcp` (Streamable HTTP per the current MCP
specification, pinned in `crates/pdx-mcp/Cargo.toml` via the `rmcp` crate version).

Authentication, either of:

- `Authorization: Bearer <access token>` obtained through OAuth 2.1 Authorization Code
  with PKCE against the configured OIDC provider. The server acts as a resource server;
  its discovery document is served at the path `/.well-known/oauth-protected-resource`.
- A PAT created in the UI, of the form `pdx_pat_…`.

Client registration follows the pinned MCP specification revision, in this order of
preference:

1. Client ID Metadata Documents, where the pinned revision defines them.
2. A pre-registered client id from `settings.mcp_client_id`.
3. Dynamic Client Registration (proxied to the OIDC provider), only as a compatibility
   fallback.

P4-08 verifies this order against the pinned revision and records it in `docs/spec/mcp.md`.
The agent never invents a registration mechanism that the pinned revision does not
define (D9).

**Local.** `pdx mcp` speaks stdio. It serves the working-tree overlay and, when
`~/.config/pdx/config.toml [server] url` is set and a token is present, forwards estate
questions to the remote endpoint and merges the results per 4.9.5.

## 4.9.2 Tools (both surfaces expose the same names)

Shared conventions, applying to every tool:

- **`view`** (optional): a signed view handle from `pdx_manifest`. Default: the current
  trunk manifest under the caller's permissions.
- **`max_output_tokens`** (optional): default `MCP_DEFAULT_BUDGET` = 4000. The ceiling is
  enforced as `4 bytes × tokens`.
- **List envelope**: all list-returning tools return `{items, total, has_more, cursor}`.
- **Cursors** encode `(view_handle, query_hash, offset)`. A cursor is rejected with error
  `stale_cursor` if the view differs.

| Tool | Input (JSON schema summary) | Output |
|---|---|---|
| `pdx_manifest` | `{refresh?: bool, manifest_name?: string}` | `{view, manifest_id, name, version, created_at, repos:[{repo_id,name,commit_sha,profile,lag_seconds,status}], local_overlay:{repo_id, merge_base, changed_files}?}`; `view` is the signed handle of 4.9.3 |
| `pdx_search` | `{query, kinds?, repos?, languages?, limit?, cursor?}` | ranked nodes: FTS (name/qualified_name/doc) with importance tie-break; optional `semantic:true` uses embeddings when the asset is installed |
| `pdx_symbol` | `{node_id}` \| `{repo, qualified_name}` | node, parent chain, signature, doc, file:line, layer role, importance, metrics |
| `pdx_callers` | `{node_id, depth? (1..5), bands? (default: drawn), limit?, cursor?}` | edges with band, evidence, and the caller nodes; grouped by repo |
| `pdx_callees` | same | same |
| `pdx_trace` | `{from_node_id, to_node_id, max_depth? (≤8), bands?}` | up to 5 shortest paths; each hop carries band and evidence |
| `pdx_blast_radius` | `{node_ids[] \| files[] \| diff_ref:{base,head}, depth? (default 3), bands?}` | affected symbols, files, services, contracts, deployments; counts per band; `unresolved_touched` (candidates rows on the path) |
| `pdx_diff_impact` | `{repo, base, head}` (local: `{}` = working tree vs merge-base) | changed symbols, blast radius summary, contracts touched, architecture rules affected |
| `pdx_architecture` | `{level: system\|context\|service\|layer\|module, focus?: node_id, repos?}` | nodes and aggregated edges at that level with `worst_band` and counts |
| `pdx_contracts` | `{kind?, key?, repo?, direction?}` | contract rows with providers and consumers across repos |
| `pdx_coverage` | `{repos?, paths?[]}` | per language/band counts; per path: status, reason, unresolved count; "no recorded gap" semantics documented in the tool description |
| `pdx_candidates` | `{node_id \| file, limit?, cursor?}` | non-drawn call sites with candidate lists and reasons |
| `pdx_snippet` | `{node_id, context_lines? (≤50)}` | source text of the node (server: `git show <commit_sha>:<path>` from the repo mirror; local: the working tree), bounded by budget |
| `pdx_definition` | `{node_id \| site_id}` | the definition(s) for a symbol or a site's callee: `precise` when a compiler provider mapped it, otherwise the structural resolution labelled with its band; search fallbacks are returned in a separate `fallback` list never labelled precise |
| `pdx_references` | `{node_id, kinds?, repos?, limit?, cursor?}` | all sites referencing the symbol (calls, reads, writes, type references, imports): from `semantic_occurrences` when a precise profile exists (labelled `provider`), otherwise from structural edges and their sites (labelled with their band); absence of a provider is reported as `provider_unavailable`, never as zero references |
| `pdx_implementations` | `{node_id}` | implementations/overrides of an interface, trait, abstract method or virtual method, from `IMPLEMENTS`/`OVERRIDES` edges with bands |
| `pdx_findings` | `{repos?, kinds?[], severity?, limit?, cursor?}` | analytics findings (4.12) with evidence |
| `pdx_feedback` | `{edge_id \| site_id, verdict, note?}` | writes `agent_feedback`; returns `{ok}` |

Result rows are compact JSON. Identifiers are never truncated. When the budget is
exceeded, whole rows are dropped from the end and `has_more = true`.

## 4.9.3 View handles

No consistency depends on transport sessions.

`pdx_manifest` mints a signed **view handle**:

```
base64url(canonical_json(claims)) + "." + base64url(HMAC-SHA256(PDX_CURSOR_KEY, payload))
```

The claims are exactly:

```
{v:1, manifest_id, permission_set_hash, overlay_hash?, mcp_tools_version, segment_schema_version, exp_unix}
```

where:

- `permission_set_hash = lowerhex(sha256(join("\n", sorted(unique(permitted_repo_ids)))))`
- `exp_unix = now + VIEW_HANDLE_TTL` (24 h)

Clients pass `view` to every tool. A handle whose permission hash no longer matches the
caller is rejected (`view_revoked`), as is an expired one. `pdx_manifest {refresh: true}`
mints a handle on the newest manifest.

Every response carries `_meta.manifest_id`, `_meta.view` and `_meta.lag_seconds` (age of
the newest segment in the manifest relative to the repo head known to the server).

Locally, `manifest_id` is `local` and the handle binds the segment content hash.

## 4.9.4 Local hooks and installer

`pdx install` writes MCP entries and hooks for the clients in Appendix E (Claude Code,
Codex CLI, Cursor, VS Code Copilot, Gemini CLI, OpenCode). It only edits keys it owns
(the `pdx` MCP entry and `pdx-*` hooks) and never modifies other entries.

Hooks:

- `PreToolUse` on `Grep`/`Glob`/`Bash` (Claude Code) and the documented equivalents: adds
  `additionalContext` with up to 10 matching symbols (`pdx_search` on the pattern), never
  blocks.
- `PostToolUse` on `Read`: if the file has coverage status other than `parsed`, adds a
  one-line note.
- `SessionStart`: injects the manifest summary (repos, lag, overlay status).

`pdx uninstall` removes exactly what `pdx install` wrote.

## 4.9.5 Local overlay

`pdx mcp` computes `merge_base = git merge-base HEAD <default_branch_remote>`, builds a
**full local segment for the active repository's working tree** (same pipeline,
`commit_sha = "worktree"`), and serves every tool as follows:

1. The remote view is requested at `merge_base` for this repo
   (`GET /api/v2/manifests/nearest?repo=&sha=` returns the manifest whose segment for the
   repo is the merge-base or its nearest ancestor, plus `overlay_distance` in commits).
2. For the active repository, **the local segment replaces the remote segment entirely**:
   nodes, edges, candidates, contracts, coverage and search results for that repo come
   only from the local segment; remote rows for that repo are never mixed in (D29).
   Row-level merging is forbidden because remote edges from unchanged files may point at
   symbols that no longer exist locally.
3. Contract links touching the active repository are recomputed locally from the local
   `contracts` table and the permitted remote contracts of other repos; trunk link edges
   touching the active repo are suppressed.
4. Everything about other repositories comes from the remote view. Estate architecture
   rows for the active repo are recomputed from local facts where the open crates can
   (L3–L5); L0–L2 fields that need the enterprise estate job are returned with
   `_meta.overlay_architecture_stale = true` rather than mixed silently.
5. Every row is marked `origin: "local" | "remote"`, and the handle's `overlay_hash` binds
   the local segment's content hash.

If no server is configured, step 1 is skipped and the local segment covers the whole
repository; estate-level questions return `unsupported_locally`.
