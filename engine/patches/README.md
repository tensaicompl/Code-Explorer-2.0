# Patches

Local changes to the vendored engine live here as patches, never as edits in place.

A refresh at a newer upstream commit re-runs the vendoring scripts, which replace the
sources wholesale, and then re-applies these. A patch that no longer applies stops
the refresh, which is the point: it means upstream changed the code underneath it and
someone must look, rather than the change being silently lost.

`scripts/vendor/apply-patches.sh` applies them in filename order and is idempotent:
the patches already applied are recognised, as the longest prefix of the series that
reverses cleanly from its last patch, and skipped.

| Patch | Why |
|---|---|
| `0001-standalone-build.patch` | The engine is built here as separate translation units. Upstream compiles it as one, which lets a source use declarations it never includes. This adds the includes the separate build needs, including three that clang rejects as implicit declarations where gcc only warns. |
| `0003-in-memory-sources.patch` | The cross-file resolution pass reads each file's source from disk. The engine interface hands it bytes instead, so this adds a thread-local provider the pass consults before the disk, and changes nothing else in it: the resolution logic runs as it was written. |
| `0002-no-analysis-subsystems.patch` | Two analyses are performed outside this engine: near-duplicate detection and structural profiling. The subsystems that computed their inputs during extraction are not vendored, so this removes both calls. The body tokens the same function produces are kept, because search depends on them. |
| `0004-supplied-crate-manifest.patch` | The cross-file pass reads the repository's root crate manifest from disk to learn its workspace members and dependencies. Reading and parsing manifests is the caller's job here, so the interface supplies the manifest already parsed, and this makes the pass take it in place of the file. The manifest's use is unchanged; with none supplied the pass behaves as the reference does for a repository without one. |
| `0006-resolution-run-record.patch` | What a typed-resolution run loses, made visible to the run (docs/plan/ISSUES.md, issue 21). The cross-file pass writes its record of the files it resolved and skipped into the project's own context. Every failed allocation is counted where it fails (`engine/api/lost_work.h`): in the memory core and the arena, and, through counting versions of the C library's allocators, at each direct allocation in the resolution sources whose failure loses work; allocations that only cost time, or whose failure falls back to the complete answer, are left as they were. Each resolver's per-file work budget counts the first time it runs out; the TypeScript resolver's two budgets are counted by `0007`, which also removes their prints. Definitions, answers and call carriers are copied whole or not at all, so a failure never leaves one half-built, and the registry no longer stores or dereferences a name it failed to copy. A test-only switch, `PDX_ENGINE_TEST_FAIL_ANSWER_ON`, fails the copy of an answer as a failed allocation would. The resolution logic is unchanged. |
| `0005-windows-thread-exit.patch` | On Windows the thread source registers a callback the loader runs as each thread exits, which releases that thread's heap in the allocator. The allocator is not linked here (`scripts/vendor/strip-list.txt`): nothing allocates from it, since every use of it elsewhere sits behind switches this build leaves off. The release was the one use outside those switches, so this puts it behind them. It also makes the callback's slot in the loader's table read-only, as the runtime's own entries are; a writable one makes Microsoft's linker warn that the table's sections disagree. The callback itself stays and still reports the thread's end. |
| `0007-typescript-budget-silent.patch` | The interface writes nothing to standard output or standard error. The TypeScript resolver printed a line to standard error the first time either of its work budgets, for parsing type text and for evaluating expressions, ran out in a file, whatever the logging switches said (docs/plan/ISSUES.md, issue 28). This replaces each print with the count of lost work the run already relies on. The budgets, and evaluation degrading to an unknown type when they run out, are unchanged. |
| `0008-no-offset-from-null.patch` | Found by the sanitizer corpus (`make check-asan`). The C# and Java resolvers build their shared registry from a copy of the project's definitions, which is NULL when the pass kept none, and then take an offset from it; with nothing to register the offset is zero, but an offset from NULL is undefined behaviour in C, which the undefined-behaviour sanitizer rejects. The cross-file pass builds the C# registry whenever extraction found any definitions, so a project whose definitions it keeps none of (a documentation-only one) reached it. This passes NULL on unchanged when there is no array. Java's builder has the same shape and no caller today; it is guarded the same way, so that the first caller does not find the defect again. |
| `0009-script-path-aliases-only.patch` | The import resolver tried a file's nearest path-alias scope before the package map for an import of any language. Aliases come from `tsconfig.json` and `jsconfig.json`, which configure TypeScript and JavaScript only, and a scope with a base URL rewrites any import that contains `/` and starts with neither `.` nor `@`: in a repository with a root configuration that sets one, a Go import of the repository's own module became a path that names nothing, and its typed resolution was lost (docs/plan/ISSUES.md, issue 43). This applies the alias step only to an importing file the engine's own lookup classes as TypeScript, TSX or JavaScript. Relative imports, the package map and Go's module mapping are unchanged. |
| `0010-site-node-type-paths.patch` | A persistent call site is identified by where it sits in its definition's syntax tree, never by its line or offset (specification 4.2.1; docs/plan/ISSUES.md, issue 46). The walk already visits every node; this records the node types of the current branch, in an arena array that grows by doubling, and remembers the depth of the innermost enclosing function. Each call and each callable reference the walk adds is stamped with its path: the node types from that function's node (or from the root, at file scope) down to the site's own node, appended to the call and usage structures as `ast_path`, NULL-terminated. Calls and references added after the walk (Rust's macro calls, Python's per-file resolution) are stamped afterwards from the tree, walking up from the site's span to the nearest function node; a site found only in preprocessed text has no span in the file and gets no path. If the array cannot grow, sites get no path rather than a wrong one. Nothing the walk extracts, and no resolution, changes. |
| `0011-route-facts.patch` | A route binding is persisted with the source site that declares it, and 4.2.4 requires every non-containment edge to reference one (docs/plan/ISSUES.md, issue 54). The engine kept one route per definition, as two strings with no position, and took the first mapping annotation or decorator it met and the first path in it. This adds `PDXERouteFact`, appended to the definition as `routes`: one fact per method and path every Spring, JAX-RS, FastAPI, Flask and Django REST framework annotation or decorator on the definition declares, each with the declaring node's span and the node types from the lowest node holding both the definition and that node down to it. A mapping listing several paths or methods gives one fact for each method and path, joined to each of the class's own mapping paths; no path is the root, no method on `@RequestMapping` is any; a path or method that is not a literal gives no fact rather than a guess. The existing `route_path` and `route_method` are computed as before, and nothing else the extractor records changes. |
| `0012-c-lsp-eval-budget.patch` | The C and C++ resolver evaluated expression types under a fixed per-file budget of 10,000 steps, a guard so that a pathological input ends in unknown types instead of hanging. The work a file needs grows with its length, and the fixed 10k budget ran out on a valid large C++ source in a golden repository, which degraded its index (docs/plan/ISSUES.md, issue 74). This makes the budget scale deterministically with source size: 10,000 steps for every started 32 KiB of the source the evaluator runs over, a minimum of 10,000 and a maximum of 320,000 (`c_eval_step_budget_for_source_len`, computed once when the context is set up, from the length alone). Small files keep the old protection, and every input still has a finite ceiling. Budget exhaustion remains lost work, counted once per file by `0006`. This patch leaves those lines untouched: the old constant's name now stands for the context's budget. The recursion-depth limit (256) is unchanged. |
| `0013-nested-modeled-call-ownership.patch` | Definitions are extracted before the unified walk, so it is known while the walk runs which callables the graph has a node for. Every function boundary pushed a function frame, which named the enclosing callable for every fact under it and also started the node-type path of every site under it. For a callable the extractor does not represent (a function nested in a function, where the definition walk does not descend into function bodies), that made it the owner: a call's caller named no definition and became the file, and the path started at the nested node (docs/plan/ISSUES.md, issue 75). Now a callable is represented exactly when its declaration occurrence (qualified name, first line, last line) is among the definitions, looked up in a set built once per walk; if the set cannot be allocated, a scan of the same definitions gives the same answer. The qualified name alone would let a nested `helper` borrow a top-level `helper`. Every callable still gets its frame as before: `enclosing_func_qn` and the lexical scope are unchanged, so typed resolution, which joins its answers to calls by that name, and parameter and local binding see exactly what they saw. For a callable that is not represented, the frame leaves the path start with the represented callable around it, and calls and possible callable references record that callable as `owner_qn`, an internal field never encoded in a surface; the interface reports it as the call's caller. Where definitions are adopted after the walk (the preprocessed pass of C, C++ and CUDA, #961 and #1989), the walk cannot know which callables will be represented, so ownership there stays by name, as before (`defs_incomplete`). `ENGINE_VERSION` 4 → 5. |
| `0014-exact-callable-owner-occurrence.patch` | Supersedes the ownership join of `0013` (docs/plan/ISSUES.md, issue 76; decision 48). `0013` decided that a callable is represented by its qualified name and lines, and the interface found a call's caller by comparing names; but the walk and the definition extractor name a callable by rules of their own, which differ for some declarations (a Rust method of a generic type, a function under a `cfg` attribute, an Ada subprogram in a package specification, a C++ test macro or template member), and those callables' sites became the file's. Now every callable definition records its declaration occurrence: the byte span of its function node (inside a C++ template, the function the template wraps) in the buffer it was extracted from, raw or macro-expanded (`PDXECallableOccurrence`, private, never in the interface, a surface or a cache). A function frame is represented exactly when its own node's occurrence is a definition's, looked up in an index built once; each call and possible callable reference records its owner's occurrence (`PDXESiteOwner`, replacing `0013`'s `owner_qn`), and the interface joins it to the definition with that occurrence, by exact equality, buffer included. A call with no position in the file is never a site: its caller stays the callable its name names, context for resolution only. `enclosing_func_qn`, the lexical scopes and every name are unchanged, so typed resolution, which joins on `enclosing_func_qn`, answers as before. A represented function node the walk cannot name (a Kotlin secondary constructor) still owns its sites; a frame that outlives its node (an error-recovered region the parser marks as trivia) never owns a site it does not hold; a site added after the walk is owned from the tree by the same rule (`stamp_late_site_owners`). For C, C++ and CUDA, `0013`'s exemption is gone: the raw walk uses the raw definitions; the preprocessed walk, before its definitions exist, records each frame's own occurrence, kept only if a definition adopted from the expanded text has it; a raw callable the adoption supersedes hands its sites to its replacement, and a raw function node standing for an adopted callable (exactly its original lines, its name on the first, no other candidate) owns the raw sites in it, both by private alias (`PDXEOwnerAlias`). Two callables sharing an occurrence would make ownership a guess: it is counted as lost work, and neither is chosen. `ENGINE_VERSION` 5 → 6. |
| `0015-source-only-preprocessing.patch` | C, C++ and CUDA extraction runs a second pass over the macro-expanded source. Its preprocessor loaded every file an `#include` named, and every file a `__has_include` asked about, from disk, relative to the process's working directory: the result then depended on where the process ran and held the content of files the interface was never given, which Stage 2 never masked, which may lie outside the repository and which no cache key names (docs/plan/ISSUES.md, issue 83; decision 51). This adds a preprocessor setting, `sourceOnly`, under which no file is opened: an `#include`, a forced include or a `__has_include` target is never found, exactly as a file that does not exist is not. The engine always sets it. The source buffer is the whole input: include directives are still in the source, where extraction reads them as imports, and the macros and conditionals the source defines itself are still expanded. Nothing else in preprocessing changes. `ENGINE_VERSION` 6 → 7. |
| `0016-fixed-date-time-macros.patch` | The preprocessing `0015` confines to the source also predefined `__DATE__` and `__TIME__` from the clock, in the process's local time zone and with the locale's month name. A source whose macros expanded either (into a call's string arguments, say) extracted differently with the time, the zone and the locale, none of which a cache key names (docs/plan/ISSUES.md, issue 84; decision 53). This adds a preprocessor setting, `fixedDateTime`, under which they are `"Jan 01 1970"` and `"00:00:00"`: the start of the Unix epoch in the library's own formats, written out rather than formatted, so that nothing is read. The engine always sets it. A source's own definition or undefinition of either still takes precedence, and no other predefined macro changes. `ENGINE_VERSION` stays 7: `0015` and `0016` together are engine 7, which had not been delivered when issue 84 was found (with `0017`, below). |
| `0017-fixed-preprocessor-sizeof-model.patch` | The same preprocessing evaluates `sizeof(type)` inside `#if` and `#elif`, an extension no compiler has, from a table it filled with the sizes of the platform the engine was built for: `long` 8 bytes on Linux and macOS and 4 on Windows, `long double` 16 on x86-64 and on Linux for AArch64 and 8 on Apple silicon and Windows. The same source and engine version could extract differently on each, and no cache key names a platform (docs/plan/ISSUES.md, issue 85; decision 54). This adds a preprocessor setting, `fixedSizeOfTypes`, under which the whole table is replaced by one written out: LP64 as 64-bit Linux has it (char 1, short 2, int 4, long 8, long long 8, float 4, double 8, long double 16, every pointer 8), for the twenty spellings the library recognises. A caller's table is ignored too, and an unrecognised spelling is still not a size. The engine always sets it. In test builds only, `PDX_ENGINE_TEST_HOST_SIZES` hands the library the sizes a build on another platform would read, as a caller's table, so that one machine can show what each platform would extract. `ENGINE_VERSION` stays 7: `0015`, `0016` and `0017` together are engine 7, which had not been delivered when issue 85 was found (with `0018`, below). |
| `0018-host-independent-literals-and-line.patch` | Two more of the same preprocessing's values came from the compiler that built it (docs/plan/ISSUES.md, issue 86; decision 55). An ordinary one-byte character constant had the value of the platform's plain `char`, so `#if '\xff' < 0` took one branch where char is signed (x86-64, Apple silicon, Windows) and the other where it is unsigned (Linux on AArch64). `#line` numbers were read with `atol`, whose C `long` is 32 bits on Windows and 64 elsewhere, so a number above 2147483647 gave different lines. Now a one-byte constant is a signed 8-bit char, written out (0x80 to 0xff are -128 to -1), and a multi-character constant a 32-bit two's complement int, also written out (the values it had on every platform); a narrow code unit is 8 bits, not `CHAR_BIT`. Other kinds (`u`, `u8`, `U`, `L`) keep their unsigned code points. One helper reads every `#line N` and `# N "file"` number: its leading decimal digits, accumulated at 64 bits and clamped to 4294967295, the largest line a location holds. No setting is needed: the conversions take no settings and the library has no other caller. `ENGINE_VERSION` stays 7: `0015` to `0018` together are engine 7 (with `0019`, below). |
| `0019-bounded-deterministic-preprocessing.patch` | The same preprocessing's work and memory were bounded by nothing but the machine (docs/plan/ISSUES.md, issue 87; decision 56). A forward `#line` within one file was padded with one newline per line skipped, so `#line 400000000` wrote 400 MB, and macros that double expanded exponentially, whether or not they created anything; recursion followed the source's nesting until the stack ran out, and folding a long `#if` restarted from the front for every ternary. This adds a `Budget` to the preprocessing library, put in force on a thread by `BudgetScope`, which the library charges as it works: the tokens and text macro expansion creates (in the token constructors and in `setstr`'s growth, only while a top-level expansion runs, so the source's own tokens copied through are never charged), the macros it expands, how deeply they nest, the bytes `stringify` writes and the tokens `#if` folding steps over. Passing a ceiling throws `BudgetExhausted`, which derives from no other exception, from inside the work, before the next allocation. `stringify` writes a forward jump of more than the budget's padding as a `#line` marker, as it writes a jump back. The engine puts its ceilings in force (`preprocessor.h`: a byte budget of 24 bytes per source byte, at least 256 KiB and at most 8 MiB, for the bytes generated, the bytes written and the folding steps; 500,000 generated tokens; 500,000 expansions; depth 256; padding 4,096 lines) and, on exhaustion, returns no expansion and counts lost work once (`pdxe_preprocess_last_stats`). `#if` arithmetic is 64-bit two's complement computed on unsigned values: sums, differences, products and the least value divided by -1 wrap, its remainder is 0, unary minus negates the number rather than prefixing its text, a shift of 64 or more gives 0, a negative count fails the condition as a division by zero does, and a negative value shifts right arithmetically, written out; integer literals are read by an explicit reader with the C++ library's results (fuzzed equal to it), so no platform's library decides one, and the classic locale formats numbers. With no `Budget` in force the library behaves as before but for the arithmetic, the integer reader and the locale. `ENGINE_VERSION` stays 7: `0015` to `0019` together are engine 7 (with `0020`, below). |
| `0020-bounded-site-node-type-paths.patch` | Every call, possible callable reference and route binding stored the node types from its owner down to itself as a whole array, so n calls nested inside one another stored about n² entries: 10,000 of them, 30 KB of C, stored 100,030,000, 954 MB in the engine (docs/plan/ISSUES.md, issue 88; decision 57). This adds one budget per file, `PDXESitePathBudget` in the result, which every producer of a path draws on through `pdxe_site_path_alloc`: the walk's paths (`current_site_path`), the paths of sites added after the walk (`late_site_path`, `owner_site_path`) and route bindings' (`route_site_path`). A path of more than 1,024 node types, or one that would take the file past 500,000, is refused before it is allocated; the first refusal counts lost work once, and after it no path is computed or allocated for the file (each producer asks `pdxe_site_paths_exhausted` first, and the climbs that size a late path stop one node past the deepest path allowed). A path is complete or absent, never cut. The sites themselves remain. A late site whose owner is not yet decided is no longer given a path by the nearest-function climb, which `stamp_late_site_owners` always replaced before anything read it; the path it keeps is the one it had. `ENGINE_VERSION` stays 7: `0015` to `0020` together are engine 7 (with `0021`, below). |
| `0021-bounded-syntax-depth.patch` | Extraction's work and memory grow faster than linearly with how deeply a file's syntax nests, in many places: a call stores its argument and callee text whole, usage scopes are found by climbing to the root with `ts_node_parent`, itself a descent from the root. A few KB of Java classes or JavaScript functions nested 1,000 deep took 45 to 56 seconds (docs/plan/ISSUES.md, issue 89; decision 58). Rather than change each mechanism, this adds one admission ceiling. `pdxe_syntax_depth_scan` walks the parsed tree once with a cursor, depth moving by one with each step (the root at depth 1, every node counted), and stops at the first node deeper than `PDXE_MAX_SYNTAX_DEPTH`, 512. It runs right after the parse and the path-only module name, before the first semantic pass; a deeper tree's result holds no fact, counts lost work once, sets `lsp_skipped` so cross-file resolution skips it, releases the tree and returns. The macro-expanded tree of C, C++ and CUDA is scanned the same way right after its parse; past the ceiling it is released and the expanded pass alone skipped, losing work once. The scan inspects every node, whatever the walk's operator budget. The result records both scans and a count of semantic passes, private, never in a surface. `ENGINE_VERSION` stays 7: `0015` to `0021` together are engine 7 (with `0022`, below). |
| `0022-linear-admitted-depth-extraction.patch` | Within the admitted depth, classifying a usage still climbed to the root with `ts_node_parent`, itself a descent from the root, for every usage, so each cost its depth squared: a 400-link Python member chain took 3 s, eight of them 25 s (docs/plan/ISSUES.md, issue 90; decision 59). The unified walk now records a frame for every node it enters (`PDXEWalkFrame`, by cursor depth: the node and the field it occupies in its parent), so the current node's ancestors are the frames below it. Each question a usage asks about its ancestors is answered from them. A nearest-of-a-kind question (global and nonlocal statements, functions, classes, parameter containers, JavaScript declarations, imports, argument lists, Perl code references and declarations, HCL attributes) is kept by each frame once computed, from the frame below. The climbs that decide a binding, a write and a Python default value keep each frame's answer for its own node: its parent's verdict on it or, undecided, the frame below's; a node of positive width has the answer of the ancestor below each deciding parent, so the frames serve it, and a node of no width (a parser's missing one) climbs the frames step by step. | `0023-bounded-external-scanner-state.patch` | The parser keeps a grammar scanner's state between tokens in a buffer of `TREE_SITTER_SERIALIZATION_BUFFER_SIZE` (1,024) bytes, and checks that it fits only in debug builds. Four of the vendored grammars' scanners did not keep it within, all of it during the parse, before the depth ceiling (docs/plan/ISSUES.md, issue 91; decision 60). YAML's serializer checked `size < 1024` before writing a four-byte pair, so from 254 nested indentation entries (510 bytes of compact sequences) it wrote two bytes past the buffer and a release build crashed in the parser; Markdown's copied every open block with no bound; Python's checked `size < 1024` before a two-byte indentation entry, one byte past the buffer when an odd number of string delimiters is open; Kotlin's called `abort()` when a 1,025th string delimiter would open. Patches must not overlap, with one exception: a later patch may supersede lines an
earlier one wrote, when it replaces that patch's mechanism for a reason of its own,
which its row says (`0014` supersedes part of `0013`, `0024` the argument copy of
`0006`, `0029` `0028`'s and `0026`'s lines in the reading of Rust `use` declarations, and
`0030` `0029`'s use map, lookup and collector). The earlier patch stays as it
was, the record of what was done and why. The applied state is recognised for the
series as a whole, as the longest prefix that reverses cleanly from its last patch on
a scratch copy, so a superseded patch is never checked against lines it no longer
owns. Any other overlap is a mistake: a change that belongs to the same reason as an
existing patch is merged into it rather than added beside it.
